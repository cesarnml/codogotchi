# Phase 20 — Sticky Slice Timestamps Retrospective

## Scope delivered

Four tickets off `v3_preview`: [P20.01](https://github.com/cesarnml/codogotchi/pull/186) bumped the slice-entry contract to schema v10, adding four optional sticky ISO-8601 fields (`prompt_started_at`, `session_started_at`, `errored_since`, `turn_ended_at`) and rewiring the hook binary's writer to read-merge prior stamps on every write instead of rebuilding the slice from scratch, so mid-turn tool ticks preserve turn-start/session-birth and only the defined lifecycle edges set or clear a stamp; [P20.02](https://github.com/cesarnml/codogotchi/pull/187) bumped Swift `EXPECTED_STATE_SCHEMA_VERSION` to 10, decoded the four stamps onto `SlicePayload`/`StateSnapshot` across every reconstruction site (including the gate-merge rebuild in `LivePollingDriver`), hydrated `PromptTimerTracker` to prefer the stamps for running/frozen elapsed (errored freeze remains app-side `errored_since + 60s` math, never hook-written), and made Force Idle's idle rewrite clear turn clocks while preserving `session_started_at`; [P20.03](https://github.com/cesarnml/codogotchi/pull/188) added a relative **Started …** subtitle fragment to Settings > Sessions rows across Active/Live/Archived, combined with existing Idle-age text on one line, omitted whenever `session_started_at` is absent; this ticket (P20.04, PR pending) updates the contract vocabulary, README release notes, and this retrospective. All four tickets ran with `subagentReview: skip_doc_only` / `skip` for docs, `prReview: disabled`, `ticketBoundaryMode` intended as `gated` per the implementation plan (see Surprises).

## What went well

- **The read-merge-before-overwrite pattern in P20.01 was the correct foundation and every downstream ticket built on it without touching it again.** Because `mergeStickyStamps` sits between "read whatever sticky fields exist on disk" and "atomically write the full slice object," P20.02's Swift decode and P20.03's Sessions subtitle only had to *consume* stamps that were already correctly preserved/cleared — neither ticket needed to reopen the write-path merge logic. One correct decision in ticket 1 removed an entire class of "did this write accidentally clobber a stamp" questions from tickets 2–3.
- **Naming the exact lifecycle-edge rules in the ticket Outcome sections (not just "add four fields") made Red tests unambiguous.** P20.01's Red section listed six concrete scenarios (preserve across mid-turn, set on prompt submit, set-once on first create, set-once on first errored, set on standby+attention, clear on idle) and P20.02 mirrored that same enumeration for the Swift side. Writing the edge list once, in exact set/clear language, and reusing it verbatim across the TS and Swift tickets meant there was no ambiguity to resolve mid-implementation about what "sticky" means at each transition.
- **Single-writer discipline for `turn_ended_at` held under adversarial review.** The ticket text explicitly forbade the menubar from writing `turn_ended_at` at the 60-second errored-freeze threshold, and both the P20.01 subagent review and P20.02's own Rationale independently confirmed the rule wasn't violated — the freeze is purely `errored_since + 60s` arithmetic in the renderer, never a slice write. Stating the "who owns this field" rule in the ticket up front prevented the natural shortcut of just writing the computed freeze time back to disk.

## Pain points

- **`readPriorStickyStamps`'s original "best-effort, swallow everything" design was an avoidable gap that the ticket's own Outcome text didn't anticipate.** The initial P20.01 implementation treated a corrupt/unreadable prior slice the same as a missing one — returning `{}` and letting the write proceed with freshly-reset clocks. This silently violated the ticket's own invariant ("mid-turn preserves session-birth") whenever the on-disk file happened to be damaged. This was avoidable: a design that distinguishes "file absent" (genuinely first-write) from "file present but unreadable" (should never be silently treated as first-write) was knowable at spec time, not just discoverable after review. See Surprises for the fix.
- **Two of three feature tickets (P20.02, P20.03) shipped with the adversarial subagent review recording an honest `skipped` outcome** (`terminatedReason: "runner_failed"` on the `cursor-cli` runner) rather than a completed pass. This is expected cost in the sense that the orchestrator's fallback-to-honest-skip behavior worked exactly as designed — no fabricated "clean" outcome — but it means the phase's two Swift/UI-heaviest tickets, precisely the surface area most prone to a missed call site (as P20.02's own Rationale found for `LivePollingDriver`), shipped without a second adversarial pass. The one ticket that did get a completed review (P20.01) found a real, patched bug.

## Surprises

- **A corrupt-prior slice could silently reset sticky clocks on the very next successful write — patched same-ticket via subagent review, not caught by the Red tests.** P20.01's adversarial review found that `readPriorStickyStamps` returned `{}` on any read/parse failure (truncated file, invalid JSON, non-object payload), and `mergeStickyStamps` then treated the absent `session_started_at` as a legitimate first-create and stamped a fresh birth time — quietly overwriting a damaged slice with reset clocks instead of refusing to write. The fix (commit `1644ea87`) split the read into `absent` / `ok` / `corrupt` states, validated prior stamp strings are real offset-datetimes before trusting them, and made the hook **fail closed**: on `corrupt`, it aborts that write entirely (writes only the read-run counter, no slice mutation) rather than persisting reset clocks. Worth generalizing: any future "read-merge prior state before write" pattern needs an explicit third state for "present but untrustworthy," not just a boolean absent/present.
- **`LivePollingDriver`'s gate-merge rebuild was a second, easy-to-miss `StateSnapshot` reconstruction site that would have silently dropped the new stamps even with a fully correct decoder.** P20.02's own Rationale flagged this directly: the reader-level decode tests all passed once `SlicePayload`/`StateSnapshot` gained the four optional members, but `LivePollingDriver.resolveRenderedPlatforms`'s gate-merge path rebuilds its own `StateSnapshot(...)` and only forwards fields it explicitly lists — any field not named there is thrown away one hop after being correctly decoded. Any future field addition to `StateSnapshot` needs to check every reconstruction call site, not just the three directory-reader call sites that are the obvious ones.
- **The `cursor-cli` subagent runner failed with `runner_failed` on both P20.02 and P20.03**, recording honest `skipped` outcomes rather than completed reviews (mirroring the `claude-cli` OAuth-expiry pattern seen in Phase 19, but with a different runner). The orchestrator behaved correctly — no silent "clean" outcome was fabricated — but it's the second phase running where more than half the tickets lost adversarial-review coverage to a runner-availability failure rather than a clean diff. The failure mode is systemic to picking a single preferred runner per phase, not specific to this phase's diff.
- **The phase's runtime delivery state recorded `ticketBoundaryMode: "cook"`, while the implementation plan's Review Rules section states `ticketBoundaryMode: gated`.** The always-pass CLI flags for this phase's delivery included an explicit `--boundary-mode cook` override on every `deliver` invocation, which took precedence over the plan-doc-declared default and is what actually ran — but it means the plan doc and the persisted `.agents/delivery/phase-20/state.json` disagree about which mode "the phase" ran in unless a reader also checks the CLI invocation history. A future phase should either update the plan doc to match the intended runtime override before delivery starts, or omit boundary-mode flags entirely and let the plan doc's declared mode be the single source of truth — mixing "doc says gated" with "every command passes cook" is a drift a future reader has no way to detect from the plan doc alone.

## What we'd do differently

The additive-optional-field-plus-lifecycle-edge-enumeration approach worked across all three feature tickets without needing revision — that part of the plan held up. Two things worth doing differently next time a "read-merge prior state on write" contract ships: (1) design the absent/corrupt/ok three-way read result from the start, in the ticket's own Outcome/Review-Focus text, rather than relying on adversarial review to catch the two-way absent/present shortcut after the fact — P20.01's ticket text didn't ask for fail-closed behavior on corrupt prior, so the first implementation reasonably (but incorrectly) treated "can't read it" as "nothing there yet." (2) When a phase's delivery intentionally overrides the plan doc's declared `ticketBoundaryMode` via CLI flags for the whole phase, update the plan doc's Review Rules line to match at the same time, so the doc stays the single source of truth instead of silently diverging from what actually ran.

## Net assessment

The phase achieved its forcing-function goal: `state.d` slices now carry durable turn/session/error clocks that survive the in-memory-tracker-loss scenarios (hide/show, TTL dismiss, fold winner changes, relaunch) that motivated the phase, the hook is the sole writer of every stamp (never the menubar, even at the errored 60s threshold), Force Idle clears turn clocks while preserving session birth, and Settings > Sessions now shows a truthful Started line that never fabricates a time for unstamped rows. The corrupt-prior gap found and patched during P20.01's own review is exactly the kind of thing a "smallest change that greens the tests" implementation misses on the first pass — the adversarial-review step did its job on the one ticket where it ran to completion.
