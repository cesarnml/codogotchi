# Phase 16 — Mechanical Consolidation ("Types and Drawers") Retrospective

## Scope delivered

Seven tickets, PRs #162–#168, stacked serially on `v3_preview` (`P16.01` directory restructure → `P16.02` `FloatingPetPanel.swift` split → `P16.03` `SettingsWindowController.swift` split → `P16.04` `WindowKey` enum → `P16.05` `SessionLifecycle` enum + classifier → `P16.06` `CustomizationStore` single writer → `P16.07` closeout audit + dogfood DMG + this retro). Net effect: zero Swift files at `apps/menubar/Sources/` root, both god-files (4,438 and ~4,700+ lines) eliminated in favor of type-per-file extraction, three new domain types replace raw-string/tuple conventions the pool and Settings previously hand-rolled, and exactly one write path exists for `customization.json`. Zero intentional user-visible change, confirmed by a clean 1047-test suite and a dogfood DMG running as the daily driver.

## What went well

- **Spine ordering (moves → splits → types → closeout) kept every PR reviewable.** Splits landed as pure extractions into already-correct drawer paths — no double-move diffs — so each split's review question stayed "does every removed line reappear verbatim in exactly one new file" rather than also asking "did the file move to the right place." Sequencing type introductions after the splits meant `WindowKey`/`SessionLifecycle`/`CustomizationStore` touched already-small, already-organized files instead of clawing through god-files.
- **`redPolicy: required` on the three type tickets caught a real behavior-changing bug before merge.** P16.04's Red phase specified round-trip tests for `WindowKey`; the resulting compiler-exhaustive sweep surfaced a genuine edge case (`RenderKeyResolver` constructing `.origin("combined")` via direct case construction instead of routing through the canonicalizing `rawValue` parse), which would have silently diverged from the pre-refactor string convention for an origin literally named `"combined"`. The fix was three lines; finding it required the Red-first discipline forcing an exhaustive round-trip test, not code review after the fact.
- **Subagent adversarial review earned its keep exactly once and it mattered.** P16.06's subagent-review pass found a real cross-instance data-loss bug in `CustomizationStore.setMode` (building `platform_modes` from a cached snapshot instead of a fresh disk read — two adapters setting different origins would drop each other's entries). This is precisely the class of bug a same-context author is structurally unlikely to catch: the ticket's own primary-agent Rationale had explicitly written "no pre-existing bug found" for the last-writer-wins concern one paragraph earlier, and was wrong for the aggregate-object case specifically. Cross-model adversarial review is worth the per-ticket cost when the ticket touches concurrent/shared mutable state, even under `skip_doc_only` policy that otherwise makes review feel optional.
- **"One ticket, no compatibility shims" for type introductions (locked in grill-me) avoided a dual-representation window.** `WindowKey`, `SessionLifecycle`, and `CustomizationStore` each landed with every consumer rewired in the same PR. The alternative (shim first, migrate consumers later) was explicitly rejected during grill-me for `WindowKey` and `SessionLifecycle` — the retrospective evidence bears this out: nothing in six tickets needed a "finish the migration" follow-up ticket, because there was no migration to finish.

## Pain points

- **Two exit-condition-wording mismatches only surfaced at closeout, not at their originating ticket's review.** The phase implementation plan's exit conditions #2 and #3 were worded more strictly ("no longer exist" / "absent from the tree"; "only WindowKey parse/serialize sites") than what P16.03 and P16.04 actually — correctly — delivered (a slimmed 408-line `SettingsWindowController.swift` orchestration residual; legitimate non-`WindowKey` `"combined"` string literals in the separate `PlatformAttribution`/assignment-origin domain). Both were *reviewed and documented as intentional* at their originating ticket's own Review Focus/Rationale, but the phase-level exit-condition prose was never reconciled against those decisions. This is avoidable waste: it cost a closeout-ticket trace-through that could have been a five-minute edit to the implementation plan the day P16.03/P16.04 merged.
- **`bun run format` was silently inapplicable for the whole phase.** P16.06's Rationale notes `biome.json`'s `files.includes` excludes `apps` entirely, so every "format → stage → commit" step in the repo's Pre-Commit policy was a no-op for every menubar-touching ticket in this phase. Nothing broke, but it means the CLAUDE.md-documented pre-commit ritual doesn't actually apply to the target this phase worked in, which is worth knowing before assuming it does on a future menubar phase.

## Surprises

- **A single grep-based exit condition can be technically false while the invariant it's protecting is fully satisfied.** Both P16.07 audit findings (items 2 and 3) are this shape: the checklist's literal command output didn't match its own predicted result, but tracing every non-matching hit to its actual call site confirmed the underlying goal (no god-files; no ad hoc `WindowKey` string branching) held. Future closeout tickets should expect this and budget time for tracing, not just running the grep.
- **`SessionLifecycle`'s second stated consumer ("menubar tiering") required no code change at all.** The ticket anticipated rewiring two consumers; `MenubarMenu`'s lifecycle tiering turned out to already fully delegate to the shared `SessionsTabViewModel` instance with no independent clock comparisons of its own, so only one file needed touching. The ticket's own Rationale flags this ("No consumer disagreement was found") — a case where the spec's risk assessment was pessimistic in a good way.
- **`ConfigFileWriter.merge`'s existing re-read-before-merge behavior already prevented the *scalar*-field version of the last-writer-wins bug** the P16.06 ticket's Review Focus was worried about — only the aggregate `platform_modes` map (rebuilt from a per-instance cache rather than re-merged from disk) was actually vulnerable. A partially-correct existing safeguard made the real gap easy to miss without adversarial review specifically targeting concurrent-write interleaving.

## What we'd do differently

- **Reconcile phase-level exit-condition prose against ticket-level Rationale the same week a ticket merges**, not deferred to the closeout ticket. The original reasoning for deferring all invariant verification to one closeout ticket (P16.07's own Rationale: "invariants can regress after their originating ticket") is still correct for genuine regression risk, but it doesn't cover wording drift between the plan and a ticket's own documented, reviewed deviation. A lightweight amendment to the implementation plan's Exit Condition section at merge time — even one sentence — would have made P16.07's audit a confirmation pass instead of a re-derivation.

## Net assessment

Phase 16 achieved its stated goal: the menubar target now has six layer directories, zero root-level Swift files, no remaining 4,000+-line god-files, and three domain types (`WindowKey`, `SessionLifecycle`, `CustomizationStore`) replacing raw-string/tuple conventions, all with zero intentional user-visible behavior change — confirmed by a 1047-test green suite and a dogfood DMG running as the daily driver at unchanged version 2.7.0. The one real bug the phase's own process caught (P16.06's cross-instance `platform_modes` clobber) was caught before merge, by design (subagent review), not after. Phases 17 and 18 inherit a genuinely cleaner foundation, not just a relocated one.
