A swallowed write failure leaves the on-disk file in its previous consistent state (the rename never committed); the next `read(at:)` returns that previous state, not garbage. **Actionable findings**

**Finding 1 — Tooltip silently never fires: `AnimationBadgePanel.ignoresMouseEvents = true` blocks `NSView.toolTip`**

File: `apps/menubar/Sources/FloatingPetPanel.swift`, lines 1664 and 2146–2155.

`AnimationBadgePanel.init()` sets `ignoresMouseEvents = true` (line 1664), making the panel window transparent to all mouse events. `PlatformSessionBadge.configure` sets `self.toolTip = ...` (line 2151) on a view inside that panel. AppKit's `NSView.toolTip` mechanism is driven by `NSTrackingArea`-based hover events, which require the window to receive mouse-entered/exited notifications. With `ignoresMouseEvents = true`, the window never receives these notifications; therefore, the tooltip string is stored on the view but can never be displayed by AppKit.

The ticket outcome states: "Hovering a session's animation badge shows, after a short delay, a truncated version of that thread's last submitted user prompt." This outcome is not achievable with the current implementation. Finding discipline clause 2 applies: the code introduces a correctness gap — the tooltip feature is wired end-to-end but silently no-ops in production.

Concrete fix paths (in order of invasiveness):
1. **Custom tooltip via global mouse monitor**: Install an `NSEvent.addGlobalMonitorForEvents(matching: .mouseMoved)` monitor in `FloatingPetPanelController` that detects when the cursor hovers over the badge panel's on-screen frame (using `NSEvent.mouseLocation` vs the panel's `.frame`) for more than ~0.5 s and then shows an `NSPopover` or custom frosted-pill window with the tooltip text. This avoids any change to `ignoresMouseEvents`.
2. **Move the `toolTip` to the pet body view**: Since `FloatingPetInteractionView` (the main pet panel's content view) already receives all mouse events, install a tracking area in it that covers the screen rect projected from the badge panel. When the pointer enters that rect, show a custom tooltip. More invasive but avoids the global monitor.
3. **Accept the gap and update the spec**: If showing the tooltip is a lower-priority nice-to-have for this ticket's 2-point budget, remove the `toolTip` assignment and update the ticket Rationale to document the deferral (matching the minimalist-mode deferral pattern already established).

**Finding 2 — Stale class doc comment on `PlatformSessionBadge` claims rename is out of scope for P15.06**

File: `apps/menubar/Sources/FloatingPetPanel.swift`, lines 2094–2097.

**Advisory Observations**

**A1 — Pool-level tooltip test coverage is asymmetric with label coverage.** Three tests cover the session-label path at the pool level (`testSessionKeyedWindowWithSidecarLabel*`, `testPlainOriginWindowNeverAppliesASessionLabelEvenIfReaderHasOne`). No symmetric tests exist for `sessionPromptSummary` / `applySessionTooltip` at the pool level. **A2 — Silent rename write failure leaves in-memory and on-disk state permanently diverged.** `SessionLabelStore.write` swallows all errors via `try?`, following the codebase's existing sidecar-reader convention (`PromptAttentionReader`, `CustomizationJsonReader`). For those sidecars (written by hooks, not the user), silent failure is acceptable. For a user-initiated rename, a disk-full or permissions error causes the badge to display the new label for the current session, but after an app restart or TTL-respawn the badge reverts to "Session N" with no error presented. The spec clause that permits this ("the CLI is untouched; app is sole writer") does not address write failure. This meets the spec, but the UX regression on failure is qualitatively different from the hook-sidecar case. No change is required to satisfy the current spec, but a future ticket could propagate write errors back to the rename alert.

**A3 — Plain-origin colon assumption is documented but not validated at the boundary.** `isSessionKeyed`'s correctness depends on no origin identifier ever containing a colon. The pool comment documents this invariant ("plain origins never contain a colon") but there is no validation in `RenderKeyResolver`, `resolveRenderKeys`, or anywhere upstream that would reject a colon-containing origin string. A future hook configuration that used a colon in an origin name would silently misclassify the plain origin as session-keyed. Low risk given current origin naming, but the assumption is load-bearing and its absence from the validation boundary is worth tracking.

**A4 — The `FloatingPetPanelController`/`FloatingPetInteractionView`/`MenubarApp` rename-UI wiring chain is completely untested.** The only tested path is the pool-level injection (`sessionLabelReader`/`appliedSessionLabels`). The `presentRenameAlert → renameHandler → onRenameRequested → SessionLabelStore.setLabel` chain in `MenubarApp.swift` and `FloatingPetPanel.swift` has no unit test. The only evidence this wiring is correct is a code review, not a test assertion. This is an acceptable gap for a 2-point ticket with `NSAlert`-modal UI, but it means regressions in the rename-callback chain would not be caught by CI.
