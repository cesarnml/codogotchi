### Ticket scope

P15.03 Per-session reader + resolveRenderKeys collapse (feat, menubar).

Outcome:

- A new reader path emits full per-session granularity: a map keyed by `origin:session_id` → `StateSnapshot`, parsing `session_id` from the slice filename (`state.d/<origin>:<session_id>.json`). Slices whose filename lacks a parseable `origin`/`session_id` are skipped; a missing session component falls back to `"default"` (matching the CLI writer's `sessionId ?? "default"`).
- A pure `resolveRenderKeys` function reduces the per-session map to the render set given the customization snapshot: Combined origins fold to `"combined"`; Own/Minimalist with session-pets **off** fold each origin's sessions to the last-writer-wins winner keyed by plain `origin`; Own/Minimalist with session-pets **on** keep each `origin:session_id` key.
- Wired into `LivePollingDriver` with the collapse running so that, with session-pets off everywhere (the default), the render set feeding the pool is **byte-identical** to today's per-origin map — every existing `FloatingPetWindowPoolTests` and `LivePollingDriverTests` case passes unchanged.
- `PerPlatformSnapshot` (or the resolved payload) carries the render-keyed map plus enough to recover `(origin, session_id)` per key for downstream labeling.

Rationale notes (from the ticket doc):

- `readPerSessionDirectory` mirrors `readPerPlatformDirectoryImpl` field-for-field (same stale-TTL filter, same `resolveActivityState`, same strict-`>` winner) so an all-default `resolveRenderKeys` collapse reproduces the per-origin map exactly; asserted directly by `testAllDefaultCollapseEqualsPerOriginMap`.
- Origin+session are parsed from the filename (split on the first colon; origin is a colon-free enum, so a `session_id` containing a colon still resolves), matching the CLI writer's `${origin}:${sessionId}.json` with `sessionId ?? "default"`.
- The driver now reads `customization.json` each tick (new injected `customizationReader`, hermetic `.safeDefault` in tests) and routes the per-platform emission through `readPerSessionDirectory` → `resolveRenderKeys` → a render-key-aware gate/context join (`resolveRenderedPlatforms`, keyed by the winning slice's origin from `identities`).
- `PerPlatformSnapshot` gained a defaulted `renderKeyIdentities` map so downstream labeling can recover `(origin, session_id)` per render key without breaking existing per-origin construction sites.
- Alternative considered and rejected: deriving the grouping origin from slice content (`sourceEvent.origin`) instead of the filename — the ticket makes the filename authoritative, and for every real slice the CLI writes filename origin === content origin.
- Deferred: the pool is unchanged this ticket; `resolveRenderKeys` folds combined-mode origins to `"combined"` at the driver while the current pool also folds combined itself — a within-stack transient resolved in P15.04 (the shipping default has no combined origins configured).

### Invariants to hold

1. 3. `resolveRenderKeys` must fold every origin whose customization mode is Combined to the single `"combined"` render key regardless of the session-pets setting, and with session-pets on must preserve every `origin:session_id` key untouched, with `identities[renderKey]` always naming the `(origin, sessionId)` of the snapshot that won that key.

### Attack surfaces to probe

1. `StateJsonReader.parseSliceFilename` — filename-parse edge cases: session ids containing colons or dots, the `.tmp-` filter using `contains` (could a legitimate slice name contain `.tmp-`?), suffix collisions (`foo.gate.json` vs an origin literally named `foo.gate`), empty session after the colon, and ordering of the guards.
2. `readPerSessionDirectoryImpl` vs `readPerPlatformDirectoryImpl` — field-for-field mirror claim: compare the stale-TTL mtime filter, the decode-failure skip, the `.fileNotFound` (missing dir) vs `.malformed` (unreadable dir) distinction in the self-scan branch vs the supplied-`listing` branch, and the `schemaVersion: EXPECTED_STATE_SCHEMA_VERSION` assignment. Any divergence breaks invariant 1.
3. `resolveRenderKeys` winner selection — Dictionary iteration order is unspecified: when two sessions of one origin share an identical `updated_at` and fold to the same render key, is the winner deterministic, and does it match what `readPerPlatformDirectoryImpl` would have picked from directory-listing order? Also probe `identities` staleness: can `states[renderKey]` be replaced while `identities[renderKey]` keeps the loser's identity (or vice versa)?
4. `LivePollingDriver.resolveRenderedPlatforms` — the legacy `gate.json`/`delivery-context.json` fallback previously fired when `perOriginMap.count == 1`; it now fires when `Set(identities.values.map(\.origin)).count == 1`. With session-pets ON and multiple sessions of one origin, the fallback now attributes the legacy gate to several windows at once — is that a behavior change vs the pre-P15.03 semantics, and is it safe? Also probe `identities[renderKey]?.origin ?? renderKey` — when can `identities` lack a key present in `renderStates`?
5. `customizationReader` per-tick read — the new default reads `CustomizationJsonReader.read(at: CodogotchiFolders.customizationPath())` every tick inside the emit path. Probe the failure mode when `customization.json` is missing or malformed mid-tick (does it degrade to safe defaults, i.e. session-pets off?), and whether the added per-tick file read happens even when no per-platform sink is attached.
6. `PerPlatformSnapshot.renderKeyIdentities` defaulted to `[:]` — probe downstream consumers of `PerPlatformSnapshot` (pool, badge routing) for any site that would misbehave when the map is empty vs populated, and whether the default hides a missed wiring site.

### Required output format

The structure is canonical and machine-parsed by downstream tooling — see

  `Advisory Observations`, `Runner termination`.
- **Do not use `---` horizontal rules anywhere in the report.** A `---`

  observation per paragraph**. Do NOT use a bold span (`**A1 — Title**`) on a
  line by itself before the observation body — that visually mimics a
  section heading and splits one labeled observation into two parsed
  observations.
