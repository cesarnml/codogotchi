**Advisory Observations**

`effectiveSessionCap(for:)` does not implement the full contract described in `CustomizationSnapshot`'s doc comment. The comment says "absent **or negative** values resolve to the default cap of 3 at the point of use (P15.04/P15.07/P15.09)." The implementation is `sessionCap[origin] ?? CustomizationSnapshot.defaultSessionCap`, which resolves only the absent case. A manually-injected negative value (e.g. `-1`) is present in the map, bypasses the `??` default, and is returned as-is. In `SettingsWindowController`, `SessionCapOption.matching(-1)` falls back to `.three` so the dropdown visually shows "3" — the UI is harmless. In `FloatingPetWindowPool.isUnlimited`, `-1 == 0` is false, so the origin is not flagged as unlimited to `SessionNumberAllocator`. However, `SessionSelectionPolicy.select` has `guard cap > 0` on line 62 and treats any `cap ≤ 0` as the unlimited-render path, so no actual sessions are blocked or lost. The practical impact is confined to manual JSON editing and is behaviorally safe, but the contract comment overpromises what P15.09 delivers. The fix (if desired) would be to add `<= 0 ? CustomizationSnapshot.defaultSessionCap : sessionCap[origin]` logic, or to narrow the doc comment to "absent values."
