**Actionable findings**

**F-1 — `releaseSessionNumber` silently no-ops for TTL-expired session-keyed windows, leaking numbers under bounded caps**

File: `apps/menubar/Sources/FloatingPetWindowPool.swift`, `releaseSessionNumber(forWindowKey:)` (~line 448).

What is wrong: `releaseSessionNumber` resolves the session identity from `currentRenderKeyIdentities[key]`, which is set at the start of each tick from `snapshot.renderKeyIdentities`. When a tool session ends and its `state.d/` file is deleted, the session key disappears from `snapshot.renderKeyIdentities` in the very next tick. The window remains alive (within the TTL window, default 5 minutes). During all subsequent ticks until TTL expiry, `currentRenderKeyIdentities[key]` is nil. When TTL finally fires and Step 5b (or the spawn guard in Step 7) tries to release the number, the `guard let identity = currentRenderKeyIdentities[key]` exits early and the release is silently skipped. The allocator's `state.assigned[sessionId]` retains the number for a session that no longer exists; the number is never inserted into `freeNumbers`. Under a bounded cap this permanently reduces the usable pool — after enough sessions, the next session gets number N+1 rather than reusing an earlier slot.

Invariant / clause: Finding clause 2 — a correctness gap demonstrable under default settings (TTL=300s, bounded cap). Normal workflow (session ends → 5-minute idle dismiss window → release skipped) triggers this on every session-keyed dismiss path.

Fix recommendation: add `private var windowIdentities: [String: RenderKeyIdentity] = [:]` to `FloatingPetWindowPool`. In `assignSessionNumber(forWindowKey:)`, after the guard succeeds, store: `windowIdentities[key] = identity`. In `releaseSessionNumber(forWindowKey:)`, look up from `windowIdentities` instead of `currentRenderKeyIdentities`, and on release clear it: `windowIdentities.removeValue(forKey: key)`. This makes release independent of snapshot staleness and mirrors the lifecycle of `windows[key]` itself.
