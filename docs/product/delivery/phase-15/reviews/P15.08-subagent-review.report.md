**Actionable findings**

**Finding 1** — `apps/menubar/Sources/FloatingPetController.swift` and the `MinimalistWindowController` class in the same file.

What is wrong: `FloatingPetController` and `MinimalistWindowController` are the concrete types stored in `FloatingPetWindowPool.windows` (typed as `[String: FloatingPetWindowControlling]`). The pool calls `windows[target]?.applyConflictBubble(ConflictBubblePayload(origin:))` and `windows[targetKey]?.applyConflictBubble(nil)`. Neither `FloatingPetController` nor `MinimalistWindowController` overrides `applyConflictBubble`, so Swift resolves both calls to the default no-op in the protocol extension (`FloatingPetController.swift:44`). The call never reaches `FloatingPetPanelController.applyConflictBubble` or `MinimalistPanelController.applyConflictBubble` because neither `FloatingPetPanelManaging` nor `MinimalistPanelManaging` declares the method, giving the adapter classes no forwarding target.

Which invariant or clause: finding-discipline clause 2 (demonstrable correctness gap — the conflict bubble is never displayed); also breaks invariants 2 and 3 (the bubble is never shown and therefore also never correctly cleared).

Concrete fix: Add `func applyConflictBubble(_ payload: ConflictBubblePayload?)` to `FloatingPetPanelManaging` (with a default no-op in its extension, matching the precedent for `applySessionNumber`) and implement a forwarding override in `FloatingPetController`:

```swift
func applyConflictBubble(_ payload: ConflictBubblePayload?) {
    panel.applyConflictBubble(payload)
}
```

Do the same for `MinimalistPanelManaging` and `MinimalistWindowController`. `FloatingPetPanelController` and `MinimalistPanelController` already have correct implementations and need no change.

**Advisory Observations**

**A1 — `activeConflictBubbleTargets` not cleared on non-resolution window teardown.** If the conflict bubble's target window is torn down by TTL expiry, mode switch, or the pending path while the origin is still in `blockedOrigins`, `activeConflictBubbleTargets[origin]` continues pointing to the now-dead key. The rate limiter suppresses re-fire for up to one hour. After the window expires, the pool would pick a new longest-lived target and fire correctly once the rate limit clears. This is per the deferred note in the Rationale ("the bubble simply disappears with that window until the next allowed fire") but is worth flagging for a subsequent cleanup pass: `activeConflictBubbleTargets.removeValue(forKey: …)` at each non-resolution window teardown site would reset the rate limiter's effective "orphaned" window to zero without affecting the timebased lockout.

**A2 — `firstSeenAt` grows unboundedly.** The dictionary is set on first sight and never compacted. For a long-running app with high session churn, this will accumulate one entry per ever-seen render key indefinitely. The `filter { currentlyRendered.contains($0.key) }` call on every tick iterates the full uncompacted dictionary. In normal use the set is small, but a cleanup sweep (e.g., mirror the `lastSeenAt` eviction pattern) would keep this bounded.

**A3 — Both bubbles stack at the same screen position when simultaneously active.** If a session is both in `blockedOrigins` (conflict bubble shown) and carrying an active `AttentionPayload` (real attention bubble shown), `BubbleLayout.frame(relativeTo: lastPanelFrame, visibleFrame:)` produces the same CGRect for both. The bubbles overlap exactly. The code's own comment acknowledges this is unlikely in practice, but there is no guard preventing the simultaneous case from reaching the screen.

**A4 — Doc-vs-code drift in ticket Rationale.** The Rationale describes the conflict bubble being delivered via the `applyConflictBubble(_:)` protocol method and received by `FloatingPetPanelController` / `MinimalistPanelController`. The documentation does not mention that `FloatingPetController` and `MinimalistWindowController` must also forward the call, nor does it note they are the types actually stored in `windows`. The missing forwarding is undocumented as an implementation requirement. If Finding 1 is patched, the Rationale should be updated to describe the two-layer forwarding chain explicitly.

**A5 — Exact 3600-second boundary not covered by tests.** `ConflictBubbleRateLimiterTests.testBlockAfterTheHourElapsesFiresAgain` uses `3600 + 1` seconds to verify re-fire. The at-exactly-3600 case (which the implementation suppresses via `> Self.window`) is not tested. The behavior is unambiguous from the code, but a boundary test at `t0 + 3600` (expect false) alongside the existing `t0 + 3601` (expect true) would fully close the boundary invariant stated in the ticket's attack surface description.
