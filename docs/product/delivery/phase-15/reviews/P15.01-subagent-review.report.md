**Advisory Observations**

The malformed-value test (`testMalformedSessionPetsEnabledDegradesToSafeDefault`) only asserts `sessionPetsEnabled == [:]` but does not also assert `sessionCap == [:]`. When the whole `CustomizationPayload` decode fails, `safeDefault` is returned and `sessionCap` is also `[:]`. Adding `XCTAssertEqual(snapshot.sessionCap, [:])` to that test case would close the gap at zero cost.

No test covers a negative `session_cap` value (e.g. `{"session_cap": {"claude_code": -1}}`). The ticket spec says negative values pass through verbatim to consumers, and the code performs no coercion, so this is correct. But because a future developer might look at the neighboring `rawTtl < 0 ? 300 : rawTtl` guard and cargo-cult a similar clamp for `sessionCap`, a brief test asserting `snapshot.sessionCap["claude_code"] == -1` would prevent that regression at low cost and make the "no clamping here" contract explicit and testable.

Silent failure on malformed JSON is the pre-existing posture of the reader and is documented, but there is no observable diagnostic surface — no log line, no metric, no `.failure` state on the returned snapshot — to distinguish "file absent" from "file malformed but present." This was a pre-existing limitation not introduced by this diff. For a system where `customization.json` is human-edited, silent safeDefault on malformed input may cause confusing UX (settings appear to silently revert to defaults). Noting this for P15.09 (Settings UI) consideration, where a "settings file invalid" signal might be surfaced to the user.
