### Attack surfaces to probe

1. `SettingsController.runHooksUpdate` — argv identity: does it really pass `["codogotchi", "hooks", "install"]` and not a stub or new `hooks update` verb?
2. `GeneralTabViewModel.refresh()` — silent-failure path: when `statusClient.fetch()` throws (parse failure or non-zero exit), does `rows` stay at its last known value rather than being cleared or crashing?
3. `GeneralTabViewModel.diagnosticsJSON()` — nil snapshot: when `lastSnapshot` is nil (refresh never called or failed), does the JSON still contain the `codogotchi` and `hookBinary` version keys?
4. `SettingsWindowController` action handlers — refresh race: `vm.refresh()` is called on the background thread before `DispatchQueue.main.async`; then `applyViewModel(vm)` is called on the main thread. Are rows read from `vm` after `refresh()` sets them, or is there a window where the main thread reads stale rows?
5. `GeneralTabView.applyViewModel` — update on error path: when an action returns an error, `setHooksError` is called but `applyViewModel` is NOT called. Does the status label show stale rows (pre-action)? Is this intentional or does it leave the user with inconsistent state when the action fails?

#### Diff-derived attack surfaces

1. **Output stability across schema-version drift** — `diagnosticsJSON()` encodes a `HooksStatusSnapshot` using `JSONEncoder` with `convertToSnakeCase`. 2. **CLI flag/arg symmetry** — No new CLI flags are added in this diff. `runHooksUpdate` calls the existing `hooks install` command — no new flag to audit. [N/A for new CLI flags, but probe argv identity above.]
3. **Error-class breadth in `catch` blocks** — `refresh()` uses `try?` which swallows all errors (both `.commandFailed` and `.parseFailed` from `HookStatusClient.Failure`). Is silent swallow appropriate here, or should command failures (subprocess error) be distinguished from parse failures?
4. **Defensive layering at module boundaries** — `GeneralTabView.applyViewModel` accepts any `GeneralTabViewModel` and directly calls `vm.rows`. 6. **Test-contract strength** — Tests for `runHooksUpdate` assert argv identity and nil/error return values. Tests for `GeneralTabViewModel` assert row count, first-row name, installed flag, refresh call, and diagnostics content. Do tests cover the nil-snapshot diagnostics case, and do they test `refresh()` failure-no-op behavior?
7. **Doc-vs-code drift in the ticket Rationale** — The Rationale says "Update genuinely rewrites the path to the current bundle" — does the diff guarantee this, or is it only guaranteed if `hooks install` rewrites? The diff delegates to the CLI entirely; the Rationale makes a behavioral claim the Swift code cannot verify by itself.
