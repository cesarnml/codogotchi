### Attack surfaces to probe

1. `build-binaries.sh` bun discovery — when `command -v bun` is empty AND none of `~/.bun/bin/bun`, `/opt/homebrew/bin/bun`, `/usr/local/bin/bun` is executable: does it `exit 1` (loud), or can control fall through and leave Resources empty while the Xcode build still reports success? Also: does `set -euo pipefail` interact badly with `$(command -v bun || true)` (unbound-var / pipefail edge)?
2. `build-binaries.sh` path quoting — the Xcode phase passes `$TARGET_BUILD_DIR/$UNLOCALIZED_RESOURCES_FOLDER_PATH`, which on some machines contains spaces (e.g. "Developer/Xcode/DerivedData/…"). Are `OUT_DIR`, `REPO_ROOT`, and the bun `--outfile` args quoted so a space-bearing path does not split into multiple args or write to the wrong location?
3. project.yml `postBuildScripts` ordering vs codesign — binaries are copied into Resources AFTER the target's code-sign step. For an ad-hoc/dev build (`CODE_SIGN_IDENTITY: "-"`) this is fine, but is there a correctness/spec-permits-real-bug risk for the eventual notarized build, and is it actually flagged rather than silently broken?
4. `ENABLE_USER_SCRIPT_SANDBOXING: NO` placement — it is set in the project-level `settings.base`, so it applies to ALL targets including `CodogotchiTests`. Is that broader than necessary, and does disabling script sandboxing weaken any protection that was previously relied on? (It was previously unset/defaulted.)
5. `.gitignore` coverage of temp artifacts — `bun build --compile` drops `.{hash}-NNNN.bun-build` temp files in the process CWD. The two invocation CWDs are repo root (`bun run build:binaries`) and `apps/menubar` (the Xcode phase `cd`s there). Does `*.bun-build` cover both, and could a temp file ever land in a path that is NOT ignored and get committed? Also confirm `apps/menubar/Generated/` actually matches the default output dir.
6. Idempotency / partial-write window — `basedOnDependencyAnalysis: false` runs the phase every build. `bun build --compile --outfile X` writes then moves; if a prior `codogotchi` in Resources is being read/executed (app running) during rebuild, is there an observable partially-written-executable window, or does bun's write-then-rename make it atomic?
