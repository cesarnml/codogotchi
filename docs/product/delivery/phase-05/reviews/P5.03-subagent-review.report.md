**Advisory Observations**

1. **Partial state on `installHooks` failure in `runSetup`** (`packages/cli/src/setup.ts:64–65`, `packages/cli/src/router.ts:174–183`): If `writeConfig` succeeds and `deps.installHooks` throws, `config.json` is left on disk. The router rethrows the unknown error as a stack trace with no message explaining the partial state. On retry, the user hits `ConfigExistsError` with no indication of what happened. Spec clause that permits it: "Write config first so `installHooks` can verify it exists." Low-risk fix: catch the `installHooks` failure in `runSetup` (or in the router handler), emit a human-readable message like `"config written but hooks installation failed — run codogotchi hooks install to complete setup"`, and rethrow. The config staying on disk is actually desirable; only the messaging is missing.

2. **`parseSetupFlags` error message says "setup" when invoked from `rpg`** (`packages/cli/src/router.ts:188`, `router.ts:93–105`): `throw new Error("Unknown flag for setup: ${arg}")` — passing an unknown flag to `rpg` emits a confusing "Unknown flag for **setup**" message. Simple fix: parameterize the command name, or create a thin `parseRpgFlags` wrapper.

3. **Raw network errors escape `runRpg` without user-friendly messaging** (`packages/cli/src/router.ts:204–214`): DNS failures, TLS errors, and connection timeouts from `doFetch` are rethrown as `TypeError` or system errors. The interactive enrollment context suggests wrapping these with a message like `"Convex registration failed: <reason>. Check your URL and network, then retry."` Not a blocking issue, but notable in a first-run UX path.

4. **`runRpg` Convex-registered-but-no-config window** (`packages/cli/src/setup.ts:217–228`): If Convex `/sync` succeeds and `writeConfig` subsequently throws (e.g., disk full), the user is registered with Convex under a `profile_id` that is never persisted. A retry generates a new UUID and creates a second orphan registration. Extremely unlikely; mentioned for completeness given the spec's emphasis on atomicity.

5. **Outcome vs Rationale drift on missing-hooks error for `rpg`** (ticket lines 14 and 44): The Outcome section promises `"if missing, error points to hooks install"` but the Rationale explicitly defers hooks-missing error surfacing for `runRpg` to a future ticket. The implementation follows the Rationale. The primary agent should align the Outcome text with the Rationale (either note the deferral in the Outcome, or open a follow-up ticket to implement the check).
