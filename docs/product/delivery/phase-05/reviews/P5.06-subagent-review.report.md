### Surface results

**S1 — `OnboardingWindowController.retryHooksInstallAction` / dead retry path**
`[probed]` — **BROKEN.** After `handleInstallSuccess` writes `onboardingCompletedAt`, clicking "⚠ Hooks not active — Retry install" in the menu calls `retryHooksInstall?()` → `onboardingController?.showIfNeeded()` → `needsOnboarding(appState:)` reads fresh state, finds `onboardingCompletedAt != nil`, and returns `false`. The callback is a no-op. A user who installed hooks, closed the sheet, then sees the persistent menu item and clicks it receives no feedback and no retry. This is the primary correctness gap in this diff.

**S2 — `handleInstallSuccess` / silent save failure**
`[probed]` — `try? appStateSaver(next)` swallows all errors with no log. If `AppStateStore.save` fails (permissions, disk full, JSON encoding error), `onboardingCompletedAt` is never persisted. The next launch reads the old state, `needsOnboarding` returns `true`, and the install subprocess runs again. For a first-launch flow this is a silent re-trigger loop with no user-visible explanation. Not data-destructive (the install command is idempotent), but the user sees the onboarding sheet every launch.

**S3 — `showPanel` / `.closable` styleMask before install**
`[probed]` — Clean. The close button is visible but `windowShouldClose` blocks it until `installSucceeded`. No "Not now" or secondary dismiss path exists in the view layer. The ticket invariant (no dismiss-without-install that marks onboarding complete) holds.

**S5 — `runHooksInstall` / argv shape passed to `defaultRunner`**
`[probed]` — Clean. `OnboardingController.runHooksInstall` passes `["codogotchi", "hooks", "install"]`. `HookStatusClient.defaultRunner` reads `argv[0]` as the ENV argument to `/usr/bin/env` and passes `argv[1...]` as `process.arguments`, yielding `/usr/bin/env codogotchi hooks install`. `[probed]` — Clean. `updateHookStatus` guards `installSucceeded` first, so a periodic hook-status refresh arriving before install completes cannot close the panel prematurely or show "Hooks not active" prematurely.

### Actionable findings

**Finding 1 — Dead retry path after install success**
`apps/menubar/Sources/OnboardingWindowController.swift` (showIfNeeded / retryHooksInstall wiring in MenubarApp.swift:170)

What is wrong: After `handleInstallSuccess` persists `onboardingCompletedAt`, the menu item "⚠ Hooks not active — Retry install" calls back to `showIfNeeded()`, which reads fresh state, finds `onboardingCompletedAt != nil`, and returns without showing the panel or retrying install. The user has no working retry path.

Clause: correctness gap (Finding-discipline clause 2).

Concrete fix: Expose a separate `retryInstall()` method on `OnboardingWindowController` that calls `runInstall()` directly — bypassing the `needsOnboarding` guard — and shows the panel if it has been closed. Wire the `retryHooksInstall` callback in `MenubarApp` to this method instead of `showIfNeeded`.

```swift
// OnboardingWindowController
func retryInstall() {
    if panel == nil { showPanel() }
    runInstall()
}

// MenubarApp (in build):
retryHooksInstall: { [weak onboardingController] in
    onboardingController?.retryInstall()
}
```

---

**Finding 2 — Silent save failure on onboarding completion**
`apps/menubar/Sources/OnboardingWindowController.swift:handleInstallSuccess`

What is wrong: `try? appStateSaver(next)` drops all errors silently. If the write fails, `onboardingCompletedAt` is never persisted; the next launch presents the onboarding sheet again and re-runs the install subprocess.

Clause: correctness gap (clause 2). Not data-destructive (install is idempotent) but creates a silent re-trigger loop.

Concrete fix: Log the failure at minimum:

```swift
do {
    try appStateSaver(next)
} catch {
    NSLog("OnboardingWindowController: failed to persist onboardingCompletedAt — \(error)")
}
```

### Advisory Observations

**A1 — Platform labeling drift from ticket spec (not patching ticket docs):**
The ticket Outcome says platforms should be "detected and labeled **deferred** or **bridge-only** per product plan." The body copy says only "coming in a future release." No runtime detection of installed agent tools runs at sheet presentation time, and neither the word "deferred" nor "bridge-only" appears. This may be an intentional scope reduction (P5.06 is scoped to Codex + Claude Code install; Cursor/VS Code detection may be deferred to a later ticket), but the Outcome section has not been annotated to reflect that. The primary agent should either add a Rationale note clarifying the scope reduction or update the copy to match the ticket's labeling intent.

**A2 — `windowShouldClose` allows close after install but before hooks active:**
After `handleInstallSuccess` sets `installSucceeded = true`, `windowShouldClose` returns `true`, so the user can close the sheet while hooks have not yet fired. The "Hooks not active" state is then only surfaced via the menu item. The ticket says "show persistent Hooks not active with next action (retry install / open Settings)" — this reads as panel-persistent, not menu-only. Combined with Finding 1 (retry is broken), the recoverable state after premature close is actually unrecoverable from the UI until the next refresh cycle shows the menu item. This is worth clarifying in the Rationale even if the current behavior is intentional.

**A3 — `@MainActor` on `refreshHookStatusCache` inherited from P5.05, not introduced here:**
The diff adds `@MainActor` to `refreshHookStatusCache`, which calls `client.fetch()` → `process.waitUntilExit()` synchronously on the main thread. This is pre-existing architecture, not a P5.06 regression, and is out of scope for this review — flagging for visibility only.
