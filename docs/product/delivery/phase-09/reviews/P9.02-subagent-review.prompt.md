### Attack surfaces to probe

1. `resolveCopilotToolAlias` case normalization — the switch uses `.toLowerCase()` before matching. Probe whether a mixed-case Copilot tool name (e.g. `"Edit"`, `"BASH"`, `"View"`) resolves correctly. An exact-match comparison would silently fall to the default case and return `"thinking"` for all non-lowercase names.
2. `normalize` origin gate for alias resolution — the alias is applied only when `rawOrigin === "vscode"`. Probe whether a payload with `CODOGOTCHI_ORIGIN` unset but `toolName: "view"` (e.g. from a Cursor payload) accidentally enters the Copilot alias path. If the gate is on the wrong condition, Cursor `view` tool names could be remapped.
3. `rawHookKind` `toolName`-as-tool_use detection — `if (input.tool_name ?? input.toolName) return "tool_use"` fires when either field is present. Probe whether a payload with `toolName: ""` (empty string) is falsy and falls through correctly, and whether a payload with only `toolName` (no `hook_event_name`) is handled correctly.
4. `withCopilotCodogotchiEntries` dedup/idempotency — the function filters out all entries where `isCodogotchiCommand(entry.command)` is true, then appends one entry per event. Probe whether `isCodogotchiCommand` correctly matches the Copilot command format (`CODOGOTCHI_HOME=... CODOGOTCHI_ORIGIN=vscode codogotchi-hook`) — specifically whether the regex `CODOGOTCHI_COMMAND_TOKEN` matches when the token is preceded by whitespace.
5. `copilotInstalled` detection in `hooksStatus` — the function checks that every event in `COPILOT_CODOGOTCHI_EVENTS` has at least one entry matching the command token. Probe whether an install file that is missing one event is correctly reported as `installed: false`, and whether an empty `hooks` array reports `installed: false`.

#### Diff-derived attack surfaces

1. **Output stability across schema-version drift** — `installVscodeHooks` writes a JSON file whose shape is `{ hooks: [...] }`. If the Copilot hooks file format changes (e.g. adds a required `version` field), the written file may be silently rejected by Copilot. Probe whether the written format matches what Copilot expects from the doc fixtures.
2. **CLI flag/arg symmetry** — `--platform vscode` is accepted by `parseHooksPlatformFlag`. Probe whether the error message for an invalid platform was updated to include `vscode`, and whether the help text for `hooks install` and `hooks uninstall` was updated.
3. **Error-class breadth in `catch` blocks** — `installVscodeHooks` calls `backupIfExists`, `readJsonOrEmpty`, and `writeText`. None of these catch their own errors explicitly; they propagate up. Probe whether a missing parent directory (`~/.copilot/hooks/`) causes a meaningful error or a silent ENOENT swallow.
4. **Defensive layering at module boundaries** — `normalize` with `rawOrigin === "vscode"` applies `resolveCopilotToolAlias` when `resolvedToolName` is truthy. Probe what happens when `resolvedToolName` is a truthy string that is not in the alias table (e.g. `"create_file"`, `"replace_string_in_file"` — Copilot tool names from the draft). These would fall to the default case, returning the original name unchanged, which then falls through `classifyEvent` to `"thinking"`. This is correct per spec ("ticket-level alias table"), but confirm it does not erroneously emit `"implementing"`.
5. **Cross-file atomicity windows** — `installVscodeHooks` calls `backupIfExists` then `writeText`. If interrupted between these, the original file is backed up but the new file is not written. Probe whether the caller or the test suite covers the partial-write case.
6. **Test-contract strength** — the idempotency test asserts `second === first` (byte-identical strings). Probe whether the JSON serialization order of the `hooks` array is deterministic. If `withCopilotCodogotchiEntries` preserves insertion order, the output is stable; if any Set/Map iteration is used, it may not be.
7. **Doc-vs-code drift in the ticket Rationale** — the ticket states "Both payload dialects: confirm a snake_case `hook_event_name` payload and a camelCase payload classify identically." Probe whether a camelCase `preToolUse` + `toolName: "edit"` and a snake_case `PreToolUse` + `tool_name: "Edit"` (both with `CODOGOTCHI_ORIGIN=vscode`) produce the same `state` and `kind`. Also check whether the `sessionEnd` behavioral change noted in Rationale is documented in the ticket's Contract note.

### Required output format

After completing your review, report in this exact structure (prose only — no file edits).
The structure is canonical and machine-parsed by downstream tooling — see
`docs/template/delivery/subagent-review-report-template.md` for the full
rules. Two rules that catch the most common drift bugs:

- Use exactly these five top-level section headings, in this order:
  `Invariant results`, `Surface results`, `Actionable findings`,
  `Advisory Observations`, `Runner termination`.
- **Do not use `---` horizontal rules anywhere in the report.** A `---`
  inside the `Advisory Observations` body breaks the all-bullets parser
  check, causes fallback to paragraph mode, and preserves `- ` prefixes
  on every observation key — creating verbatim-match churn in the
  downstream dispositions file and forcing `---` itself to be triaged as
  a fake observation. Just omit `---`.
- **`Runner termination` must be the section heading**, not `**runnerStatus:**
  \`completed\`` or any other inline key-value variant. Write it as the bold
  span `**Runner termination**` on its own line, then `runnerStatus:` and
  `terminatedReason:` as plain-text lines below. Any other format leaves the
  termination block inside the `Advisory Observations` body.
- Inside `Advisory Observations`, write **one observation per bullet or one
  observation per paragraph**. Do NOT use a bold span (`**A1 — Title**`) on a
  line by itself before the observation body — that visually mimics a
  section heading and splits one labeled observation into two parsed
  observations.
