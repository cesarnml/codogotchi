**Actionable findings**

**Finding 1 — `hooks install --help` omits `vscode` platform.**
File: `packages/cli/src/router.ts`, lines 436 and 452–453.
Both the `--help` output and the "unexpected args" error message for `hooks install` read `[--platform <claude_code|cursor>]`. The `vscode` platform was added to `parseHooksPlatformFlag` and to the `hooks uninstall` help text, but the two `hooks install` strings were not updated. A user following `--help` output will not discover that `--platform vscode` is valid for install, contradicting the ticket Outcome ("Router accepts `--platform vscode` for hooks install/uninstall").
Discipline clause: correctness gap (finding-discipline clause 2) — the documented interface does not match the implemented behavior for `hooks install`.
Fix: change both strings from `[--platform <claude_code|cursor>]` to `[--platform <claude_code|cursor|vscode>]`.

**Finding 2 — `copilotInstalled` throws when called with a `hooks`-less file.**
File: `packages/cli/src/hooks.ts`, lines 260–264 (`copilotInstalled`) and line 839 (`hooksStatus`).
`copilotInstalled(file)` calls `file.hooks.some(...)` directly. `hooksStatus` passes `copilotJson` — the raw result of `readJsonOrEmpty<CopilotHooksFile>(copilotPath)` — without ensuring `hooks` is an array. If `~/.copilot/hooks/codogotchi.json` exists on disk but contains `{}` or `{ "hooks": null }` (e.g., created by a partial external tool or a truncated write), `file.hooks` is `undefined` or `null`, and `file.hooks.some` throws a `TypeError`. All other platforms guard the hooks field with `(x.hooks ?? {})` before use; the vscode path omits this.
Discipline clause: correctness gap (finding-discipline clause 2) — `hooksStatus()` throws on a reachable external file state.
Fix: in `hooksStatus` (line 839), normalize before calling `copilotInstalled`:
```
const normalizedCopilot: CopilotHooksFile = {
  hooks: Array.isArray(copilotJson.hooks) ? copilotJson.hooks : [],
};
const vscodeFullyInstalled = copilotInstalled(normalizedCopilot);
```
Alternatively, add `if (!Array.isArray(file.hooks)) return false;` as the first line of `copilotInstalled`.

**Advisory Observations**

Missing test for Copilot `sessionEnd → standby`. The `describe("Copilot (vscode) native hook classifier")` block covers `agentStop → standby` but has no corresponding case for `hook_event_name: "sessionEnd"`. The Outcome explicitly lists both; the code correctly handles both via the `rawEventName === "agentstop" || rawEventName === "sessionend"` guard. The gap is in test coverage, not code.

Cross-dialect fixture symmetry gap. The two camelCase/snake_case fixture files (`pre-tool-use-camel.json`, `pre-tool-use-snake.json`) test different tool names (`"edit"` vs `"view"`), so they don't verify that the same tool name produces the same state via both field paths. A test pairing `{ tool_name: "edit", hook_event_name: "PreToolUse" }` and `{ toolName: "edit", hook_event_name: "preToolUse" }` both asserting `implementing` would close this gap explicitly.

`partially_installed: false` is hardcoded for vscode. If `COPILOT_CODOGOTCHI_EVENTS` gains a new event in a future ticket, existing installs will flip to `installed: false` with no `partially_installed: true` transition, which is asymmetric with the cursor/claude_code/codex upgrade path. Not a bug in this ticket's scope; worth noting before the next platform event expansion.

`uninstallVscodeHooks` test coverage is narrow. The test at `hooks.test.ts:1005–1011` checks `raw.not.toContain("codogotchi-hook")` but reads from the file if it exists (`existsSync(hooksPath) ? readFileSync(...) : ""`). If uninstall had deleted the file instead of cleaning it, the empty-string path would also pass. The code correctly writes a cleaned file rather than deleting it, but the test does not assert the file still exists with valid JSON.

Outcome description of `web_fetch` is slightly misleading. The Outcome says `web_fetch → reading` implying a direct mapping; the code routes `web_fetch → "WebFetch"` (alias table), then `WebFetch` is in `READING_TOOL_NAMES` → `reading`. The final state is correct; the description skips the intermediate alias and may mislead a future reviewer who searches for a direct `web_fetch` → `reading` entry.
