### Ticket scope

**Outcome:**
- SoA gate states (`hyped`, `calling_for_backup`, `waiting`, `celebrating`, `nervous`, `focused`, `panicking`, `ascended`) persist in `state.json` through subsequent tool_use events.
- A gate state is cleared only when: (a) a new SoA gate event fires, or (b) a `session_end` / `stop` event arrives.
- `.hook-counters.json` gains a `last_gate: { state: ActivityState, fired_at: string } | null` field.
- When `last_gate` is set and the incoming event is a tool_use (not a gate or session_end), `runHook` emits `last_gate.state` rather than the heuristic result.
- `fired_at` is an ISO 8601 timestamp of when the gate originally fired — unused in Phase 06, present for Phase 07 gate TTL.

**Rationale notes:**
- `GATE_STATES` is extracted from `Object.values(SOA_GATE_TO_STATE)` to avoid hardcoded duplication.
- Stickiness override happens after the SoA tail read, not before.
- `session_end` and `stop` both clear `last_gate` (both map to `"session_end"` kind in `rawHookKind`).
- `fired_at` uses `opts.now` (current invocation time) as an approximation when gate came from SoA tail. Known approximation; Phase 07 TTL will use this field.
- Old `.hook-counters.json` without `last_gate` is treated as `null` (backwards-compatible).

### Invariants to hold

1. When `last_gate` is set in `.hook-counters.json` and an incoming event is classified as `tool_use`, `runHook` must write `last_gate.state` as `activity_state` in `state.json` — never the heuristic tool_use result.
2. A `stop` / `session_end` event must set `last_gate` to `null` in `.hook-counters.json` after `runHook` completes, even when `last_gate` was previously non-null.
3. A new SoA gate event must overwrite `last_gate` with the new gate state; subsequent tool_use events must then emit the new gate state, not the prior one.

### Attack surfaces to probe

1. **`stickiness block` ordering in `runHook`** — the stickiness logic reads `classified.sourceEvent.kind` (computed before the SoA tail read). If a fresh SoA gate arrives via the tail, it sets `activityState` to a gate state. The stickiness block then checks `GATE_STATES.has(activityState)` which fires correctly. But if `classified.sourceEvent.kind` is `"tool_use"` and a fresh SoA gate also arrived, does the gate win or does the sticky-override branch fire? The `else if` structure means the gate check fires first (condition 1), so the override branch (condition 3) cannot fire on the same invocation — but verify this holds in the code.

2. **`parseLastGate` with malformed or partial input** — if `.hook-counters.json` contains `last_gate: { state: 42, fired_at: "..." }` (non-string state) or `last_gate: { state: "hyped" }` (missing `fired_at`), does `parseLastGate` correctly return `null`? A corrupted `last_gate` that passes through as a valid `LastGate` could permanently lock `activityState` to a stale gate value.

3. **`session_end` detection for errored Stop** — when a Stop event has `is_error: true`, `classifyEvent` returns `{ state: "errored", sourceEvent: { kind: "session_end" } }`. The stickiness block checks `classified.sourceEvent.kind === "session_end"` to clear `last_gate`. Verify that `errored` stop events also clear `last_gate` (i.e., the session_end branch fires because `errored` is not in GATE_STATES and sourceEvent.kind is "session_end").

4. **`GATE_STATES` completeness** — `GATE_STATES` is derived from `Object.values(SOA_GATE_TO_STATE)`. Note that `ticket_completed` and `review_clean_recorded` both map to `"celebrating"` — `GATE_STATES` contains `"celebrating"` once (Set deduplication). Verify this doesn't cause the check to miss a gate state.

5. **Concurrent invocations and `last_gate` persistence** — `runHook` uses `withHomeLock` for mutual exclusion. Verify that `last_gate` is read inside the lock scope (not before the lock), so two concurrent hooks don't see stale `last_gate` values and race-write different outcomes.

6. **`.hook-counters.json` write includes `last_gate`** — verify the `writeCounters` call at the end of `runHook` passes `last_gate: lastGate`. A missing field in the write would silently reset `last_gate` to undefined on the next read (which `parseLastGate` would return as null), breaking persistence after one gate event.
