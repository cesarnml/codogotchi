**Diff-derived Surface 3 — Error-class breadth in `catch` blocks** — `[probed]`
Both catch branches at lines 250–253 return the zero-value object with `last_gate: null`. A JSON parse error (malformed file) and an IO error (ENOENT) are treated identically. **Diff-derived Surface 4 — Defensive layering / invalid state string through cast** — `[probed — finding]`
`parseLastGate` checks that `candidate.state` is a `string`, then casts it directly to `ActivityState` (line 233) without checking it is a _valid_ member of `ActivityState`. If `.hook-counters.json` contains `{ "last_gate": { "state": "definitely_not_valid", "fired_at": "2025-01-01T00:00:00Z" } }`, `parseLastGate` returns `{ state: "definitely_not_valid" as ActivityState, ... }`. This value then becomes `activityState` at line 398 and is written into `state.json` under `activity_state`. Whether `stateJsonV1Schema.parse` then rejects it depends on the schema — if it does, the process throws and the hook exits with an error on the next tool_use call until the counters file is cleared. See **Actionable Finding 1**.

**Diff-derived Surface 5 — Cross-file atomicity window** — `[probed]`
`writeStateAtomic` runs first (line 414), then `writeCounters` (line 415), both inside `withHomeLock`. If the process is killed between the two writes, `state.json` is updated but `last_gate` retains its previous value in counters. On the next hook invocation: if the killed invocation was a gate-fire, counters still have the old `last_gate` (or null) — the new gate did not persist. If the killed invocation was a session_end, `last_gate` still contains the old gate value — it won't be cleared until the next session_end survives to the counters write. Both scenarios result in a stale `last_gate` that drives an incorrect sticky state for exactly one subsequent tool_use event (the next hook call will then re-fire whatever event arrives, which will re-evaluate and potentially correct the state). This is a narrow partial-write window, bounded to one event, and consistent with the pre-existing atomicity model. **No new bug beyond pre-existing window; partial-write semantics are acceptable given lock+atomic-rename design.**

**Diff-derived Surface 6 — Test-contract strength** — `[probed — gap found]`
Tests assert `state.json` activity_state after each step but **do not assert the `last_gate` field in `.hook-counters.json`** at any point. This means a regression that correctly writes `state.json` but silently drops `last_gate` from counters (breaking persistence across invocations) would not be caught by the current tests — it would only be detected on the _next_ tool_use call if that test checks state after the second invocation, which the existing test does. However, the intermediate counters state after a gate fire is never directly verified. See **Advisory Observation 2**.

The `errored` Stop path (Stop with `is_error: true` following a gate event) is not tested for `last_gate` clearance. See **Advisory Observation 1**.

**Diff-derived Surface 7 — Doc-vs-code drift in ticket Rationale** — `[probed]`
The ticket Rationale states: _"fired_at is an ISO 8601 timestamp of when the gate originally fired — unused in Phase 06, present for Phase 07 gate TTL."_ It also states: _"fired_at uses opts.now (current invocation time) as an approximation when gate came from SoA tail. Known approximation."_

The code at line 391 always uses `opts.now.toISOString()` regardless of whether the gate came from direct hook input (where the timestamp of the original event would theoretically be knowable) or from the SoA tail. The Rationale acknowledges this approximation for the SoA tail case, but the code uses the same approximation for direct gate input too — the Rationale doesn't call this out explicitly for the direct-input case. Since `fired_at` is unused in Phase 06, there is no observable behavioral consequence. **Minor doc imprecision, not a code bug.** See **Advisory Observation 3**.

### Actionable Findings

**Finding 1 — Invalid `ActivityState` string passes `parseLastGate` and reaches `stateJsonV1Schema`**

- **File:** `packages/cli/src/hook-binary.ts`, line 233
- **What is wrong:** `parseLastGate` validates that `candidate.state` is a `string` but does not validate that it is a _member of `ActivityState`_. A `.hook-counters.json` with `last_gate.state` set to any arbitrary string passes the function and is cast to `ActivityState`. On the next tool_use call, the invalid string is assigned to `activityState` (line 398) and written to `state.json`. If `stateJsonV1Schema` enforces an enum on `activity_state`, the write throws and the hook crashes for every subsequent tool_use until the counters file is manually cleared or overwritten by a fresh gate/session_end event.
- **Clause:** Finding discipline 2 — correctness gap.
- **Fix recommendation:** Add an `ACTIVITY_STATES` set (e.g., `new Set<string>(["standby", "idle", "implementing", ...])`) and check `ACTIVITY_STATES.has(candidate.state)` before the cast in `parseLastGate`. Return `null` if the check fails. Alternatively, reuse the `ActivityState` runtime set already established by `GATE_STATES` as a partial guard and add the remaining non-gate activity states. This ensures only valid enum members persist through `last_gate`.

### Advisory Observations

- **Obs 1 — Missing test: errored Stop clears `last_gate`.** Surface 3 confirms the code is correct for errored Stop events. But no test fires a gate, then sends a `Stop` with `is_error: true`, and asserts both that `state.json` shows `errored` and that a subsequent tool_use no longer sticks to the gate. This path is the only meaningful divergence from the clean-Stop path, and it is entirely untested in the sticky-gate test suite.

- **Obs 2 — Tests never read `.hook-counters.json` directly.** All sticky-gate tests assert only `state.json`. A regression that silently drops `last_gate` from the counters write (e.g., someone removes `last_gate: lastGate` from the `writeCounters` call) would not be caught until the _second_ tool_use invocation in a multi-step test. The two existing multi-step tests happen to cover this, but asserting `counters.last_gate !== null` directly after the gate-fire step would make the test invariant more explicit and less brittle.

- **Obs 3 — `fired_at` approximation is broader than Rationale states.** The ticket Rationale describes `fired_at` as an approximation only "when gate came from SoA tail." In practice, `opts.now.toISOString()` is used for all gate sources (line 391), including direct hook input where the event's own timestamp is not available from the hook input shape. The Rationale is slightly imprecise (the approximation is universal, not SoA-tail-specific). Since `fired_at` is unused in Phase 06, no behavioral impact exists today, but the Phase 07 TTL author should be aware that `fired_at` is always the _hook invocation time_, not the gate emission time, regardless of source.
