**Actionable findings**

- `apps/menubar/Sources/AssignmentsJsonReader.swift:35-38`, `apps/menubar/Sources/AssignmentsJsonReader.swift:85-90`, and `apps/menubar/Sources/PetTabViewModel.swift:157-167` — a successful valid platform assignment can leave disk and memory inconsistent when `assignments.json` already exists as a readable JSON object but lacks a non-empty `default`. `AssignmentsJsonReader.read` returns `safeDefault`, but `AssignmentsJsonWriter.write` only seeds `default` when the file is absent, so `assign(badge: "claude_code", to: "pet-a")` writes only `claude_code`; the in-memory snapshot gains the override while a fresh reader still returns safeDefault and drops it. This breaks invariant 2. Fix: have the writer seed `default: DEFAULT_PET_NAME` whenever a non-default write targets an existing payload whose `default` is missing, non-string, or empty; add a test starting from `{"schema_version":1}`.

- `apps/menubar/Sources/PetTabViewModel.swift:146-167` and `apps/menubar/Sources/AssignmentsJsonReader.swift:85-101` — `assign` accepts arbitrary badge strings. For `badge: "foo"`, the ViewModel exposes `foo` in `badges(for:)` and fires the callback, but `AssignmentsJsonReader` ignores that key on relaunch; for `badge: "schema_version"`, the writer can overwrite the schema field with a pet id. This is a correctness gap against the 5-platform-plus-Default assignment contract, and P14.03 explicitly delegated badge-key enforcement to P14.07. Fix: validate `badge` against `ASSIGNMENT_BADGE_KEYS` before `isInstalled`/write, throw a typed `invalidBadge` error, and assert no snapshot/disk/callback change for invalid keys.
