**Actionable findings**

- `apps/menubar/Sources/AssignmentsJsonReader.swift:83-85` with `apps/menubar/Sources/ConfigFileWriter.swift:18-39` — `AssignmentsJsonWriter.write(badge:petId:to:)` can create an unreadable assignment from the caller’s perspective on a fresh URL when `badge` is any non-default platform key. Example path: `write(badge: "claude_code", petId: "shiba", to: missingURL)` writes `schema_version` and `claude_code` but no mandatory `default`; `AssignmentsJsonReader.read` then returns `safeDefault` and drops the just-written assignment. This is a correctness gap against the writer outcome that a single badge assignment is persisted. Fix: when the target file is absent or lacks a valid `default`, either seed `default: DEFAULT_PET_NAME` as part of the write or throw a typed error requiring migration/default seeding before non-default writes.

- `apps/menubar/Sources/AssignmentsJsonReader.swift:111-124` — `AssignmentsMigration.seedIfAbsent` is not race-safe. The spec’s absent-file seed clause permits a `fileExists` check followed by `ConfigFileWriter.merge`, but if another process creates `assignments.json` in that window, `merge` loads the new file and overwrites its `default` key with the migrated `config.pet`/fallback value. That is a spec-permits-real-bug data-loss exposure. Fix: use exclusive create semantics for migration seed, matching `ConfigBootstrap.writeExclusive`/`O_EXCL`, and treat `EEXIST` as a no-op instead of merging into the concurrently-created file.
