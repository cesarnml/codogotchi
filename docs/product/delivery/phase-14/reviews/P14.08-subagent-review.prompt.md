### Attack surfaces to probe

1. **`makeCard(for:)` entry-state guard** — the `if entry.state == .importable` branch adds the import button; the `else` branch for installed pets adds the assign button inside the name row. Probe whether a card for an importable pet could accidentally get an assign button in the name row, or vice versa.
2. **`badgeMenuItemClicked(_:)` → `viewModel.unassign` path for "default" badge** — `unassign(badge:from:)` is a no-op when `badge == "default"`. If the user opens the dropdown on the Default-holding pet and tries to toggle Default off, the model silently no-ops, but the menu item was shown with `.on` state. Probe whether this produces confusing UI (item cannot be unchecked but is presented as checkable).
3. **`objc_setAssociatedObject` key collisions** — `assignBtnKey`, `badgeMenuItemKey`, and `importBtnKey` are three distinct `UInt8` static vars. Probe whether all three keys are unique and whether any previously-used `actionKey` was removed cleanly (no leftover references).
4. **`rebuildGrid()` after badge toggle** — `badgeMenuItemClicked` calls `rebuildGrid()` synchronously after `assign/unassign`. The rebuilt grid re-evaluates `viewModel.badges(for:)` and re-draws the badge pills and Default border. Probe whether `onAssignmentsChanged` (the live-swap side-effect) and `rebuildGrid()` can produce a race or double-execution that leaves the grid in an inconsistent state.
5. **`onAssignmentsChanged` wiring completeness in `SettingsWindowController`** — the live-swap chain requires `petTabViewModel.onAssignmentsChanged → onPetActivated → MenubarApp.reloadActivePet()`. Probe whether all links exist in the controller and whether the removal of `handleSelectPet` leaves any path where a Default badge change through the assign dropdown would NOT reach `reloadActivePet()`.
