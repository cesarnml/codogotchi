### Attack surfaces to probe

1. **`isInstalled` freshness in `assign`** — `isInstalled` calls `directoryNames(in: canonicalPetsRoot)`
   on every invocation (no caching). A pet imported between `catalog()` and `assign()` in
   the same session could be rejected. Probe: is the live filesystem check correct, or can
   a race produce a false "not installed" rejection for a just-imported pet?
2. **`assign` no-op for "default" badge** — The no-op guard checks `assignmentsSnapshot.default`
   for the "default" badge and `platformOverrides[badge]` for others. Probe: what happens
   when `badge == "default"` and `petId` is already the default holder (`currentHolder == petId`)?
   Is the early-return correct or does it misidentify the current holder?
3. **`isDefault` in `catalog()` vs. snapshot staleness** — `catalog()` reads
   `assignmentsSnapshot.default` at call time. After `assign(badge: "default", to: newPet)`,
   the snapshot is updated in-memory. Probe: does a second `catalog()` call after `assign`
   return the updated `isDefault`, or is there a stale read path?
4. **`unassign` silently ignores write failures** — `unassign` uses `try?` and returns
   early on failure, leaving in-memory state and disk in sync. Probe: is the guard
   `(try? ConfigFileWriter.merge(...)) != nil` actually sufficient to detect all disk
   write failures, or can it silently succeed while writing nothing (e.g., when
   `assignmentsURL` path doesn't exist and parent-dir creation fails)?
5. **`SettingsWindowController.handleSelectPet` uses `try?`** — `handleSelectPet` calls
   `try? petTabViewModel.assign(badge: "default", to: id)`. If `assign` throws (e.g., for
   an importable pet — which shouldn't be selectable from the UI but could arrive via a
   stale card), the error is silently swallowed and the UI's `refreshPetList` fires anyway.
   Probe: does the view render consistent state when `assign` is silently suppressed?
6. **`onAssignmentsChanged` callback in `SettingsWindowController`** — The callback
   closure captures `self?.petTabViewModel.assignmentsSnapshot.default` after assignment.
   Probe: is `self?.petTabViewModel` guaranteed non-nil at callback time, or can the
   controller have been deallocated between `assign` completing and the closure executing?
