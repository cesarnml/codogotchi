### Ticket scope

P21.03 Fallback advances on ran-but-failed runners

`runSubagentWithFallback` (`tools/delivery/subagent-runner.ts`) now advances to the next
runner in `buildSubagentFallbackOrder` when an attempt returns `status: 'ran'` with
`terminatedReason` in `{runner_failed, rate_limit, sandbox_denied}` — the issue #105 case
where the CLI spawns and exits but the backing model produced no usable review.
`advisory_violation` does not advance the chain (it is decided after the loop, from write
detection, not `terminatedReason`, so it never reaches the new check). `skipped` with
`fallbackLevel: 'failed_all'` is recorded only when every runner in the chain fails; every
attempt remains auditable in `attemptedKinds`. A successful fallback records `fallbackFrom`
= the originally requested runner and `fallbackLevel: 'fallback'`, exactly as the existing
unavailable/timeout path did.

Rationale (from the ticket doc): the change broadens `shouldFallbackToOtherRunner` to also
return `true` for `ran` results with the three failure `terminatedReason`s, and gates the
loop's early-return on that same predicate — the smallest change; loop shape and
`attemptedKinds`/`fallbackLevel` bookkeeping were untouched. A second, `ran`-specific
predicate function was considered and rejected in favor of broadening the single existing
function, per the ticket's own Refactor note anticipating a possible need to unify two
homes.

A pre-existing test describe block (`P11.04 — auto-fallback predicate is narrowed to
binary-availability failures` in `tools/delivery/test/p11-04.test.ts`) asserted the exact
old, narrower contract this ticket reverses; its two `it` blocks were flipped to assert the
new `true` outcome instead of being left contradicting the new behavior.
