### Attack surfaces to probe

1. **`seedRpgState` in `hook-binary.ts` — tiebreak correctness**: does it correctly use `new Date(parsed.updated_at).getTime()` for wall-clock comparison, never filesystem mtime? Does it correctly return `null` when no v7 slices exist (so the caller falls through to computed v5 values)?

2. **`runHook` write ordering in `withHomeLock` — slice-before-rpg window**: `writeSliceAtomic` is called first, then `rpg-state.json`. If the process is killed between the slice write and the rpg-state write, is the resulting state safe (slice written, rpg missing)? Can consumers tolerate a missing rpg-state.json?

3. **`sliceEntrySchema.strict()` — field exhaustion**: does `.strict()` catch all six removed RPG fields? Does it also reject other unknown fields that might have accumulated in v7-era on-disk slices?

4. **`writeRpgStateAtomic` — missing `mkdir`**: `writeStateAtomic` calls `mkdir(home, { recursive: true })` before writing. `writeRpgStateAtomic` skips `mkdir`. If `home` doesn't exist yet (edge case before the outer `mkdir` in `runHook`), does this cause ENOENT?

5. **`seedRpgState` — state.json fallback gap**: the ticket spec says "(2) `state.json` if no v7 slices", but `seedRpgState` only scans `state.d/` and returns `null` with no `state.json` fallback. Is this a spec-permits-real-bug or an acceptable simplification?

6. **`runHook` rpg-state.json write — `rpg_enabled: false` path**: when `rpg_enabled` is false, `v5` is `null` and `rpg-state.json` is never written. If a user later re-enables RPG, the first write will trigger migration seed from v7 slices that also won't have RPG fields (they were written during the disabled period). What happens?

### Required output format

The structure is canonical and machine-parsed by downstream tooling — see

- **Do not use `---` horizontal rules anywhere in the report.** A `---`

  termination block inside the `Advisory Observations` body.

  observation per paragraph**. Do NOT use a bold span (`**A1 — Title**`) on a
  line by itself before the observation body — that visually mimics a
  section heading and splits one labeled observation into two parsed
  observations.
