### Invariants to hold

1. The pool must never dismiss the window whose origin has the most-recent `updated_at` timestamp across all ever-seen origins, regardless of elapsed wall-clock time.
2. `readPerPlatformDirectory` must return `.failure(.fileNotFound)` when the directory does not exist; `.success([:])` when the directory exists but all slices lack a parseable non-empty origin.

### Attack surfaces to probe

1. `lastUpdatedAt` vs `lastSeenAt` separation — `lastActiveOrigin` is elected from `lastUpdatedAt` (snapshot timestamps), while TTL dismissal is measured from `lastSeenAt` (wall-clock). If `lastUpdatedAt` for a stale origin is higher than the newly-active origin's `lastUpdatedAt`, the stale origin becomes `lastActiveOrigin` and is immune to TTL while the active origin gets dismissed. Probe whether this can happen legitimately (e.g. clock skew between two AI agents writing slices).
2. Combined-mode window TTL interaction — the combined window is keyed "combined", not by an origin. `lastSeenForWindow("combined")` reads max `lastSeenAt` across all combined-mode origins listed in `platformModes`. But if a combined-mode origin appears in a snapshot but is NOT in `platformModes` (platformModes is empty `[:]` by default), its `lastSeenAt` is never consulted, and `lastSeenForWindow("combined")` returns nil → the combined window would always be treated as stale (dismissed if not last-active).
3. Off-mode origins bleeding into combined aggregation — verify the filter ordering: `filter { mode(for: $0.key) != "off" }` runs first, then combined/own split. If an origin has mode "off" but also appears in visibleEntries (due to a bug in the off filter), can it contribute to the combined window's winner computation?
4. `StateJsonReader.readPerPlatformDirectory` empty-origin filter — the code guards `!origin.isEmpty` for the `winners` dict key. Verify that an origin that is a whitespace-only string is also excluded (the guard only checks `!origin.isEmpty`, not trimmed-empty).
5. Pool factory `fatalError` on nil self — `MenubarApp` stores the pool strongly, the pool captures `[weak self]` in the factory. If app teardown calls pool's factory after `MenubarApp` is deallocated (e.g., a timer-fired applyPerPlatform during teardown), the fatalError fires. Probe whether `applicationWillTerminate` stops the driver before the pool can receive new snapshots.
6. `MenubarMenu` weak pool reference — `MenubarMenu` stores `floatingPetPool` as `weak var`. If the app drops its strong reference to the pool (e.g., during `reloadActivePet`), the menu silently shows "Show Pet" (disabled). Is there a code path where `MenubarApp.floatingPetWindowPool` is set to nil without also rebuilding `MenubarMenu`?

### Diff context

Key logic changes:

1. **FloatingPetWindowPool.update()** uses two tracking dicts: `lastSeenAt[origin] = currentTime` (TTL clock) and `lastUpdatedAt[origin] = max(existing, stateDate)` (for last-active election). `lastActiveOrigin` = argmax of `lastUpdatedAt`. The window key for `lastActiveOrigin` is immune to TTL dismissal. Stale keys are those where `currentTime - lastSeenAt[key] > ttlSeconds` (and not the last-active key).

2. **Combined mode TTL gap**: `lastSeenForWindow(key:)` for key "combined" returns `platformModes.keys.filter { platformModes[$0] == "combined" }.compactMap { lastSeenAt[$0] }.max()`. If `platformModes` is `[:]` (default in P13.04), this always returns `nil`, meaning the combined window would be evaluated as `nil → true` (stale) on every tick after the first. However, the combined window is also the last-active window in this scenario (only one window exists), so it would be immune. But if there are also own-mode origins, the combined window could be non-last-active and get wrongly dismissed immediately. This is a potential bug.

3. **MenubarApp pool factory**: `saveState: { _ in }` suppresses per-window persistence. This means all pool-created `FloatingPetController` instances share the same initial position from `app-state.json` but don't write back. On the first tick after pool creation, all pool windows will appear at the same screen position (stacked on top of each other). This is the documented P13.04 deferral.

4. **applyPerPlatform wiring**: `driver.applyPerPlatform = { [weak self] snapshot in ... self?.floatingPetWindowPool?.update(snapshot: snapshot) }` — the pool is accessed via `weak self` through two optionals. If either is nil, the update is silently dropped. On the first tick after MenubarApp init, both should be non-nil.
