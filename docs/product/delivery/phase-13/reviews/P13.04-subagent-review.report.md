## Adversarial Review — P13.04 FloatingPetWindowPool + LivePollingDriver

---

### Invariant Results

**Invariant 1 — `broken`**
The pool must never dismiss the `lastActiveWindowKey` window regardless of elapsed time. For own-mode origins, step 5's immunity guard correctly protects the window. For combined-mode origins, step 5 also correctly marks "combined" immune—but step 8's else branch (`else { windows["combined"]?.setFloatingPetVisible(false); windows.removeValue(forKey: "combined") }`) fires unconditionally whenever `combinedOrigins.isEmpty`, with no `lastActiveWindowKey` check. The combined window is dismissed even when it is the last-active window, breaking the invariant. Concrete trace: `platformModes = ["claude_code": "combined", "cursor": "combined"]`, TTL = 60s. After tick 1 (both origins visible, combined window spawned, `lastActiveWindowKey = "combined"`), at t = 61s with empty snapshot: step 5 marks "combined" immune and `staleKeys = []`, but step 8 unconditionally removes it.

**Invariant 2 — `held`**
`readPerPlatformDirectoryImpl` guards `fm.fileExists(atPath:, isDirectory:)` at line 282; returns `.failure(.fileNotFound)` when absent. When the directory exists but all slices fail the `!origin.isEmpty` guard (line 311), `winners` stays empty, `result` is `[:]`, and `.success([:])` is returned. Both clauses confirmed.

**Invariant 3 — `held`**
`visibleEntries = snapshot.perPlatform.filter { mode(for: $0.key) != "off" }` runs before any window spawning (step 1). Both own-mode (step 7) and combined-mode (step 8) window creation paths operate on `visibleEntries` exclusively. `windowFactory` is unreachable for off-mode origins.

### Surface Results

**Surface 1 — `lastUpdatedAt` vs `lastSeenAt` separation — `probed`**
`lastUpdatedAt[origin]` is only ever updated upward (line 59–61) and is never cleared when an origin disappears from the directory. A single slice with a far-future `updated_at` (clock skew between AI agents is realistic: wall-clock differences of hours are possible between a macOS host and a remote agent) permanently claims `lastActiveOrigin`. The associated window then receives the TTL immunity in step 5 and is never dismissed, rendering as a ghost with stale frozen state while real active agents' windows are correctly subject to TTL. The spec says "active origins" but the implementation elects from "ever-seen origins"; this gap is production-unsafe even if the ticket wording technically permits it.

**Surface 2 — Combined-mode window TTL interaction — `probed`**
Confirmed as the mechanism for the Invariant 1 break above. When `platformModes` maps origins to "combined" but those origins have left the snapshot (due to mtime staleTTL after ~2h of inactivity), `lastSeenForWindow("combined")` correctly aggregates the last-seen timestamps, but the step 8 else branch fires before any of that matters and unconditionally dismisses the window. The combined window is not afforded the same structural immunity as own-mode windows.

**Surface 3 — Off-mode origins bleeding into combined aggregation — `probed`**
The off-filter (`!= "off"`) runs at step 1 on `snapshot.perPlatform`. `visibleEntries` excludes off-mode origins. `combinedOrigins` at step 6 is derived from `visibleEntries`. `lastSeenForWindow("combined")` uses `platformModes.keys.filter { platformModes[$0] == "combined" }`, which returns origins mapped to "combined" not "off". No bleeding path exists.

**Surface 4 — Whitespace-only origin string — `probed`**
Line 311: `guard let origin = slice.sourceEvent?.origin, !origin.isEmpty`. A whitespace-only string `"   "` passes `!origin.isEmpty`. Such an origin would be keyed in `winners` and produce a `StateSnapshot` result. The pool would call `windowFactory("   ")` and spawn a window for it. `displayName(for: "   ")` falls through to the default case (`origin.replacingOccurrences(of: "_", with: " ").capitalized`) producing a whitespace string, which would appear in the menu as "Hide   Pet". This is a real correctness gap — the guard should check `!origin.trimmingCharacters(in: .whitespaces).isEmpty`.

**Surface 5 — Pool factory `fatalError` on nil self during teardown — `probed`**
`applicationWillTerminate` calls `livePollingDriver?.stop()` at line 471, which invalidates the timer. The `Timer` fire block (`Task { @MainActor in self?.runTick() }`) cannot be in-flight after invalidation on the same `@MainActor` context. Since `runTick` is the only caller of `applyPerPlatform`, and `applyPerPlatform` is the only caller of `windowFactory`, no post-stop factory call is possible under normal shutdown. `MenubarApp.floatingPetWindowPool` is never set to nil (confirmed: `reloadActivePet` does not touch it). No real risk.

**Surface 6 — `MenubarMenu` weak pool reference — `probed`**
`floatingPetWindowPool` is set once at launch (line 211) and is never reassigned or nilled elsewhere. `reloadActivePet` (line 383) updates only `codexPet`, `codogotchiPet`, and renderer. `MenubarMenu` is constructed with the strong-held pool before the pool reference could become nil. No silent "Show Pet" regression path exists.

**Diff-derived Surface 1 — Schema drift — `probed`**
`SlicePayload` (line 382) omits all RPG fields. `Decodable` silently ignores unknown keys. A v7 slice containing `level`, `halfHearts`, etc. parses cleanly. RPG data in the pool comes from `PerPlatformSnapshot.rpgSnapshot` (read from `rpg-state.json`), not from per-platform `StateSnapshot` RPG defaults. No schema regression.

**Diff-derived Surface 2 — CLI flag/arg symmetry — `N/A`**
This ticket adds no CLI flags; changes are Swift/AppKit only.

**Diff-derived Surface 3 — Error-class breadth in catch blocks — `probed`**
Corrupt JSON slices are silently skipped via the chained `guard let data ... let slice` at line 309–312. Silent skip is the correct posture for a per-origin directory scan: one bad slice should not block the others. No partial-read error is surfaced; this is an intentional product decision.

**Diff-derived Surface 4 — `.failure(.fileNotFound)` on first launch — `probed`**
In `runTick` (line 230–234): `applyPerPlatform` is only called when `perPlatformResult` is `.success`. When state.d/ doesn't exist, `readPerPlatformDirectory` returns `.failure(.fileNotFound)`, the if-case guard is false, and `applyPerPlatform` is not called. Pool receives zero updates. `activeOrigins = []`. Menu shows "Show Pet" (disabled). Correct.

**Diff-derived Surface 5 — Cross-file atomicity — `probed`**
`FloatingPetWindowPool` is `@MainActor`. `windowFactory` returns synchronously. The spawn sequence (lines 91–95) runs synchronously without suspension points. No off-thread access exists. No atomicity risk.

**Diff-derived Surface 6 — Test-contract strength — `probed`**
`testOriginWithExpiredTTLIsDismissedButLastActiveWindowSurvives` correctly exercises the immunity logic: "claude_code" is explicitly dismissed and "cursor" explicitly survives. The test would fail if the immune window were incorrectly dismissed. However, there is no test covering the combined-mode lastActive case—where step 8's else branch dismisses the combined window despite step 5's immunity. The gap directly covers the Invariant 1 break.

**Diff-derived Surface 7 — Doc-vs-code drift — `probed`**
Ticket says "most-recently-active window (most-recently-updated origin across all **active** origins)." The implementation maintains `lastUpdatedAt` across **ever-seen** origins (updated only upward, never cleared). This is confirmed by the lack of any cleanup of `lastUpdatedAt` when an origin disappears. The behavior diverges from the ticket's "active" framing when a gone origin holds a higher `lastUpdatedAt` than any current origin. See Surface 1 finding above.

### Actionable Findings

**Finding 1 — Invariant 1 broken for combined-mode last-active window**
- File: `apps/menubar/Sources/FloatingPetWindowPool.swift`, lines 124–130 (step 8 else branch)
- What is wrong: The else branch dismisses `windows["combined"]` unconditionally when `combinedOrigins.isEmpty`, regardless of whether "combined" is `lastActiveWindowKey`. Step 5's TTL immunity is correctly computed but then overridden by step 8. This breaks Invariant 1 for any pool configuration using combined mode.
- Clause: Finding discipline 1 (invariant break).
- Fix: Add a `lastActiveWindowKey` guard in the else branch:
  ```swift
  } else if windows["combined"] != nil && "combined" != lastActiveWindowKey {
      windows["combined"]?.setFloatingPetVisible(false)
      windows.removeValue(forKey: "combined")
  }
  ```
- Also add a test: seed combined-mode pool with two origins, advance clock past TTL, feed empty snapshot, assert combined window survives.

**Finding 2 — Clock-skewed `updated_at` permanently claims `lastActiveOrigin` → ghost window**
- File: `apps/menubar/Sources/FloatingPetWindowPool.swift`, lines 59–66 (lastUpdatedAt update + lastActiveOrigin election)
- What is wrong: `lastUpdatedAt[origin]` is never reset or clamped. A slice file written once with a far-future `updated_at` (clock skew, e.g. an agent running under a system clock 2h ahead) permanently holds `lastActiveOrigin` after that origin stops appearing in state.d/. Its window remains visible indefinitely—a ghost showing frozen state—and no real active agent's window can displace it as the TTL-immune slot.
- Clause: Finding discipline 3 (spec-permits-real-bug: the ticket's "ever-seen" behavior is not explicitly forbidden, but it is production-unsafe).
- Fix recommendation: Clamp `lastUpdatedAt` to `min(stateDate, now())` to prevent future-dated timestamps from locking the election, or reset `lastUpdatedAt[origin]` when `lastSeenAt[origin]` exceeds `ttlSeconds` by a safety margin (e.g., 2× TTL). The simpler fix is the clamp: `let stateDate = min(StateJsonReader.parseISO8601Date(state.updatedAt) ?? currentTime, currentTime)`.

**Finding 3 — Whitespace-only origin string bypasses guard**
- File: `apps/menubar/Sources/StateJsonReader.swift`, line 311
- What is wrong: `!origin.isEmpty` passes for `"   "`. A hook bug or malformed slice could write `source_event.origin = "   "`, which would key a window with a whitespace origin and produce a malformed "Hide   Pet" menu item.
- Clause: Finding discipline 2 (correctness gap).
- Fix: `!origin.trimmingCharacters(in: .whitespaces).isEmpty` (or a trim-and-assign to also normalize the key).

### Advisory Observations

- **Double filesystem read per tick.** `runTick` reads state.d/ twice per tick: once via `reader(pollingTargetPath)` (global aggregate for the menubar) and once via `StateJsonReader.readPerPlatformDirectory(at: pollingTargetPath)` (per-origin for the pool). On a slow filesystem or with many slice files, this doubles per-tick I/O. The two reads are not atomic—a concurrent agent write between them could produce a global-aggregate snapshot for menubar and a per-platform snapshot that don't agree on which origin "won." This is a pre-existing architectural tension rather than a P13.04 bug, but the new per-platform read makes it two reads where there used to be one.

- **`saveState: { _ in }` causes all pool windows to stack at the same initial position.** The factory suppresses per-window persistence (line 193). On the first tick after pool creation, all spawned windows will appear at the identical screen position from `app-state.json`. This is documented in the diff context as a P13.04 deferral, but there is no ticket reference or `TODO` comment in the factory body. A future developer may not know this is intentional. Adding a single `// P13.04 deferral: per-window position persistence not yet implemented` comment in the factory block would prevent a "why is saveState suppressed?" confusion.

- **`pool.activeOrigins` is sorted `Array(windows.keys).sorted()`.** `menubarMenu.buildPetSection` enumerates `origins` in sorted order to build hide items. Menu items for "Claude Code" and "Cursor" would always appear alphabetically rather than by recency of activity. For P13.04 this is fine, but when per-window position is added, the user might expect the most-active pet's item first.

- **`applyPerPlatform` has no caching guard, unlike all other sink emissions.** `applyAttention`, `applyGateBadge`, `applyPlatform`, and `applyRPGState` all have change-detection caches (`lastAttentionEmission`, `hasEmittedGateBadge`, etc.) to suppress identical repeats. `applyPerPlatform` has none—it emits on every tick that reaches a `.success` result from `readPerPlatformDirectory`. Since pool update is idempotent (spawning an existing window is a no-op), this is harmless for correctness, but it means `FloatingPetWindowPool.update()` runs every 1Hz even when state is unchanged, doing a full `visibleEntries` filter + TTL pass each time.
