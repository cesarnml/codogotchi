**Actionable findings**
1. `convex/actions/uploadPet.ts:32-39` and `convex/pets.ts:27-37` — The per-user rate limit is enforced with a separate query before the write, so concurrent requests can both pass and create an 11th upload inside the 24-hour window. This breaks the ticket outcome’s “rate limit is enforced” clause and is a correctness gap. Fix by moving the quota check into a mutation-scoped transaction or by introducing a transactional per-user counter/lease row that is checked and incremented atomically with pet creation.

2. `convex/actions/uploadPet.ts:57-77` and `convex/pets.ts:55-64` — The action deletes the raw upload before uniqueness is enforced and before the `pets` row exists, then stores the canonical blob before `createPet`. On duplicate-slug or later mutation failure, the caller gets an error, the raw upload is already gone, and the canonical blob is leaked without any row pointing to it. This is a demonstrable correctness gap and also a spec-permits-real-bug under the rationale sentence at `docs/product/delivery/phase-11/ticket-03-upload-action.md:43` that says the raw zip is deleted “regardless of outcome.” Fix by checking slug uniqueness before deleting the raw blob, and wrap canonical-store/createPet in rollback logic that deletes the canonical blob if the mutation fails; only delete the raw blob after the durable row exists or inside a compensating cleanup path.

3. `convex/actions/uploadPet.ts:69-74` — Oversized thumbnails are silently dropped from the row but never deleted from storage, so every oversized upload leaks an unreferenced blob. This is a correctness gap tied to the ticket’s thumbnail-handling behavior. Fix by calling `ctx.storage.delete(resolvedThumbnailId)` when a fetched thumbnail exceeds `MAX_THUMBNAIL_BYTES`, ideally in a best-effort cleanup block that cannot mask the main action result.
