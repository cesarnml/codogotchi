### Invariants to hold

1. The stored `zipStorageId` on the `pets` row must reference the canonical re-packed zip, never the raw uploaded bytes. If the raw zip is stored directly, the trust boundary is broken.
2. An unauthenticated caller (getAuthUserId returns null) must never insert a `pets` row or store any permanent blob. The raw zip must be either deleted or never referenced in a `pets` row.
3. If validation fails (result.ok === false), no `pets` row must be inserted and the canonical zip must not be stored — only the raw zip cleanup may occur.

### Attack surfaces to probe

1. **Raw-vs-canonical zip confusion in `uploadPet` handler**: The raw zip is fetched, the validator runs, the raw is deleted, THEN the canonical is stored. If `validateAndRepackPet` returns `ok: true` but `canonicalZip` is empty or equal to the raw bytes (e.g., validator bug), the canonical storageId still differs from the raw one — but could there be any path where the raw storageId leaks into `createPet`? Probe the variable binding: `rawZipStorageId` is the arg, `canonicalZipStorageId` is the new store result. Verify no aliasing.
2. **Rate limit window race**: `countRecentPetsByAuthor` uses `Date.now() - RATE_LIMIT_WINDOW_MS` as the `since` cutoff. This call happens before the `createPet` mutation. Two near-simultaneous requests from the same user could both pass the rate-limit check (both see count < 10) and both insert, yielding count=11. Assess whether this is an acceptable MVP trade-off or a correctness gap.
3. **petId sanitization producing collisions**: `sanitizePetId` replaces all non-alphanumeric chars with "-" and trims leading/trailing "-". Two distinct raw petIds (e.g., "my pet!" and "my-pet") both map to "my-pet". The second call would throw a duplicate slug error, which is the correct behavior per spec, but the error message says "already in use" — probe whether the error message is surfaced to the caller correctly.
4. **Thumbnail size check vs. storage.get failure**: If the thumbnailStorageId points to a blob that no longer exists (`ctx.storage.get` returns null), `resolvedThumbnailId` is set to null. This is safe. But if the thumbnail blob IS oversized, the action does not delete it — the oversized thumbnail remains in Convex storage unclaimed. Probe whether this creates orphaned storage blobs.
5. **Raw zip cleanup on validation failure**: After `validateAndRepackPet` returns `ok: false`, `ctx.storage.delete(args.rawZipStorageId)` is called, THEN `throw new ConvexError(...)`. Verify the delete completes before the throw — if delete is awaited properly, this is fine. But if delete throws itself (e.g., storage ID not found), the validation error is swallowed by the delete error.
