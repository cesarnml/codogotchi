### Invariants to hold

1. `validateAndRepackPet` must return `{ ok: false }` when either `spritesheet.webp` or `codogotchi-lite-basic-spritesheet.webp` is absent from the input zip.
2. The canonical zip output must contain only the 5 allowlisted filenames; any input entry with a path traversal (`..`) prefix or a non-allowlisted name must be absent from the output zip.

### Attack surfaces to probe

1. `validateAndRepackPet` → traversal guard: `name.includes("..")` — does it catch all zip-slip patterns an attacker could craft? Consider URL-encoded paths, `./` prefixes that shadow allowlisted names, backslash separators.
2. `validateAndRepackPet` → allowlist check vs. path prefix: a zip entry named `./spritesheet.webp` is not in the allowlist (only `"spritesheet.webp"` is) — so it is silently stripped. But this also means a completely valid zip assembled with `./`-prefixed entries would be rejected as "missing required files." Is there a stripping race condition where a required entry is present but silently dropped before the required-file check?
3. `validateAndRepackPet` → per-file size cap read order: `file.async("uint8array")` is called before `content.length > MAX_FILE_BYTES` — the full file content is read into memory before the cap fires. A malicious zip could include a giant file that allocates memory before being rejected.
4. `validateAndRepackPet` → `image-size` error surface: `sizeOf(Buffer.from(content))` for an unknown or corrupt image — `sizeOf` throws on unrecognized format. The `try/catch` catches this. But what happens when `sizeOf` returns a result with `width` defined as `0`? The guard `!dims?.width` is falsy for `width === 0`, which would silently treat a 0-width image as passing the dimension check without triggering the divisibility error.
5. `validateAndRepackPet` → total-size counting only counts files that passed per-file cap: files exceeding `MAX_FILE_BYTES` are pushed to `errors` and `continue`d before `fileSizes[name]` is set. This means `totalBytes` only accumulates the valid subset. A zip constructed so that the 5 MB file is the ONLY oversized file would correctly fail, but a zip with 3 large-but-under-cap files could hit `MAX_TOTAL_BYTES` correctly — verify the math is sound.
6. `validateAndRepackPet` → `pet.json` key validation: the implementation checks `id` and `display_name` with two separate if-blocks that both re-check `typeof parsed !== "object" || parsed === null`. If `parsed` is not an object at all, both push errors independently. But the `id` check also fires when `id` exists but is not a string — which is correct. Verify edge case: `{ "id": null }` — `typeof null !== "string"` is `true`, so the error fires. But `"id" in parsed` would be `true` for `{ "id": null }`, so `!("id" in parsed)` is false, and then `typeof parsed.id !== "string"` is `true`. Result: one error is pushed. Is `id: null` correctly rejected?
