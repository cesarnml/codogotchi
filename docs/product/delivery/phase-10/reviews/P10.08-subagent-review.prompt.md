### Attack surfaces to probe

1. `PetConfig.write(rpgHUDEnabled:to:)` — features-key type coercion: if the existing config has `"features"` stored as a non-dict value (e.g. `null`, array, or string), `(obj["features"] as? [String: Any]) ?? [:]` silently replaces the whole features block with `{"rpg_hud_enabled": <value>}`, potentially stripping `rpg_enabled` and other keys that the CLI schema requires.
2. `PetConfig.write(rpgHUDEnabled:to:)` — round-trip serialization: `Bool` in `[String: Any]` serializes to JSON `true`/`false` via `JSONSerialization`. Verify this survives a read-back cycle with `resolvedRPGHUDEnabled(from:)` which casts `as? Bool`.
3. `SettingsTab.rawValue` shift — inserting `.rpg` (rawValue 2) between `.pet` and `.developer` shifts `.developer` from rawValue 2 to 3 and `.about` from 3 to 4. Any code that hardcodes or persists tab rawValues could silently select the wrong tab after upgrade. Probe `SettingsWindowController` tab initialization and any persisted selection state.
4. `RPGTabView.onToggle` closure — retain cycle risk: `RPGTabView` holds `onToggle` strongly; `SettingsWindowController.openWindow` passes `{ [weak self] enabled in self?.rpgTabViewModel.setRPGHUDEnabled(enabled) }`. Verify no strong self capture creates a cycle through the view hierarchy.
5. `RPGTabViewModel.init` config-read failure path — when the config file exists but contains malformed JSON (empty file, truncated JSON), `resolvedRPGHUDEnabled(from:)` returns `true` (the safe default). Verify the init path uses the same failure-safe path, not a try! or force-unwrap variant.
