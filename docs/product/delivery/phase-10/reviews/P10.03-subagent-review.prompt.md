### Attack surfaces to probe

1. superRefine null vs undefined for last_activity_at: the schema declares last_activity_at as
   .nullable().optional(). A v5 payload with last_activity_at: null must PASS the superRefine
   check (null !== undefined). A v5 payload where last_activity_at is absent must FAIL. Probe
   whether data[field] === undefined correctly distinguishes null from absent in the Zod-parsed
   output for a .nullable().optional() field.

2. schemaVersionField max boundary: the field is z.number().int().min(1).max(STATE_JSON_SCHEMA_VERSION).
   After the bump to 5, version 5 must be accepted and version 6 must be rejected. Probe whether
   the max check correctly rejects 6 and accepts 5 — particularly, does the schemaVersionField
   run BEFORE superRefine, so a version-6 input is rejected by the field validator rather than
   reaching the superRefine check?

3. rpgConfigSchema half-configured cloud state: cloud fields are now individually optional. A
   payload with convex_http_url but no handle, or handle but no convex_http_url, passes schema
   validation. Is this a correctness gap? The ticket rationale explicitly defers "all-or-none"
   enforcement. Probe whether any existing CLI code reads cloud fields under the assumption they
   are always present together when rpg_enabled is true — if so, that code may now silently
   receive undefined where it previously received a string.

4. hearts.ts re-export chain: engine/hearts.ts now imports from @codogotchi/contracts and
   re-exports the constants. The resolveHalfHearts function body uses HALF_HEART_DECAY_HOURS and
   ACTIVE_MINUTES_PER_HALF_HEART. Probe whether the import brings the constants into the module
   scope where the function runs, not just re-exports them. If the import is present but the
   re-export uses a separate `export { }` block without the import, the function would fail at
   runtime with "not defined."

5. superRefine Array<keyof typeof data> field list completeness: the superRefine iterates over
   ["level", "level_fraction", "half_hearts", "last_activity_at"]. Probe whether all four keys
   exactly match the field names declared in the .object() block — any typo (e.g. "last_active_at")
   would produce a superRefine that silently always passes for that field, because data["last_active_at"]
   would be undefined regardless of the input.

6. rpg_hud_enabled default behavior: the schema declares rpg_hud_enabled: z.boolean().optional()
   — no default value. The ticket says "Opt-out flag default true so existing installs keep the
   HUD unless they opt out." Probe whether the schema enforces a default of true, or whether the
   application must handle the undefined case in each call site. If the schema does not enforce
   the default, is there a risk that consumers read undefined as false?
