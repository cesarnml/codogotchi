### Ticket scope

**Outcome:**
- On hook events, the CLI computes the full v5 progression locally and writes it into state.json with zero cloud config required.
- XP: incrementally tallies cumulative tokens across claude and codex only (Antigravity is HP-only). Tracks a per-source last-read position so re-runs do not double-count. Computes level + level_fraction via levelForXp/levelProgress.

**Rationale:**

- Falls back to schema_version 4 when config is absent or rpg_enabled is false — existing v4 readers unaffected.
- v5 fields (level, level_fraction, half_hearts, last_activity_at) written only when rpg_enabled === true.

### Attack surfaces to probe

1. `computeAndPersistV5Fields` — cursor overlap edge: event at exactly `parseSince(last_read_at_claude)` ISO. The JSONL filter is `event.timestamp < sinceIso` (strict less-than). If last_read_at_claude equals an event's timestamp, that event is re-included on the next read — potential double-count for the exact-boundary case.
2. `computeAndPersistV5Fields` — prevLastActivityAt snapshot: the code snapshots `cache.last_activity_at` BEFORE updating it to `now`. If the cache read and the snapshot happen within the same lock but another concurrent hook fires between cache read and snapshot... but actually the withHomeLock in runHook prevents this. Verify the V5 compute is inside the lock scope.
3. `readConfig` error propagation: the try/catch in runHook catches all errors from both readConfig and computeAndPersistV5Fields. If readConfig throws a ConfigReadError (invalid config), the outer catch silently swallows it and falls back to v4. Is this correct — could a user with an invalid config get stuck on v4 forever without warning?
4. `active_minutes % 60` reset — off-by-one in heal consumption: after `resolveHalfHearts({activeMinutes: 60, currentHalfHearts: 5}, now)`, healGain = 1, result = 6. Then `active_minutes = 60 % 60 = 0`. If the SAME call had `activeMinutes: 61`, healGain = 1, active_minutes = 1. Both correct. But verify: if activeMinutes accumulates to 120 in a single call path (bug?), healGain = 2 and remainder = 0 — is this reachable?
5. `withHomeLock` scope: does `computeAndPersistV5Fields` run INSIDE the lock acquired by `withHomeLock`? If it runs outside, concurrent hooks could race on the local XP cache producing double-counted tokens.
6. JSONL parse error handling: if the JSONL file is malformed/unreadable, `readJsonlSignals` throws. The `try/catch` around it in local-xp-writer still advances `last_read_at_claude` to `now` on failure. This means a persistent read error would silently advance the cursor, permanently skipping tokens that were unreadable at the time. Is this the right behavior, or should the cursor not advance on failure?
