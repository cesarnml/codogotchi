**Actionable findings**

- `apps/menubar/Sources/Pool/Derive/PoolDerive.swift:189` — Origins absent from `sessionCapKeysByOrigin` never execute the slice replacement at lines 224–226. Reproduction: render one session for origin A, then tick with no surviving session candidates for A; `memory.slotOccupants` still contains the old key. This breaks invariant 2 and the ticket’s slot-occupancy-resync outcome. Iterate the union of current candidate origins and origins represented in existing session slot occupants, selecting with an empty session map for absent origins, or explicitly clear absent-origin slices before the current loop. Add a candidates-to-zero test.

- `apps/menubar/Sources/Pool/Derive/PoolMemoryUserActions.swift:60-74` — `pruning(_:)` claims derive will release the captured identity next tick, but line 71 removes the exact prior-membership evidence used to form `torndownKeys`. When the paired prune deletes the slice before the next tick, `visibleFinalKeys` and `previousKeys` both omit the key, so lines 273–277 never release it. This breaks invariant 3 and the release-on-teardown contract. Release and remove the captured identity directly inside `pruning(_:)`, as `hiding(_:)` does, or retain a separate pending-teardown record that derive consumes. Add an end-to-end prune → absent-snapshot → lowest-number-reuse test.

- `apps/menubar/Sources/Pool/Derive/PoolDerive.swift:189-198,275-277` — Allocator mode is refreshed only for current candidates or fresh spawns. If an assigned origin changes bounded↔unlimited on the same tick its candidates disappear, teardown releases under the stale prior mode: bounded→unlimited incorrectly adds the number to the free list; unlimited→bounded incorrectly discards a reusable number. This is a demonstrable gap in the unlimited-cap semantics. Before any releases, refresh allocator mode for every origin represented by captured identities being torn down, using `resolvedSessionCap`; add tests for both cap-change directions with an absent current snapshot identity.
