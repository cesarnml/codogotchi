Findings

- **P1 — Reversed shadow ignores persisted hidden keys.**  
  [`FloatingPetWindowPool.swift:1668`](/Users/cesar/code/codogotchi_p18_06/apps/menubar/Sources/Pool/FloatingPetWindowPool.swift:1668) initializes `LegacyPoolEngine` with `hiddenKeysLoader: { [] }`, while the new engine loads the real hidden-key set at line 1675. On launch with a persisted hidden window, the new engine suppresses it but the legacy shadow spawns a stub and reports a divergence. This makes reversed-shadow soak results unreliable. Pass the loaded hidden set into both engines while keeping the shadow saver inert.

- **P1 — `sessionNumber` returns released numbers after hide/prune.**  
  [`sessionNumber(forWindowKey:)`](/Users/cesar/code/codogotchi_p18_06/apps/menubar/Sources/Pool/FloatingPetWindowPool.swift:1866) returns `primaryMemory.sessionNumbers[key]` without checking active membership. `PoolMemory.hiding` and `.pruning` release the allocator identity but never remove `sessionNumbers[key]`. After `setVisible(false)` or `pruneSession`, the accessor still returns the old number for a key with no controller, violating the public-surface contract and potentially reporting a number later reused by another session.

- **P2 — `sessionDisplayLabel` remains stale after immediate teardown.**  
  [`sessionDisplayLabel(forWindowKey:)`](/Users/cesar/code/codogotchi_p18_06/apps/menubar/Sources/Pool/FloatingPetWindowPool.swift:1871) reads `lastDesired`, which is not invalidated by `setVisible(false)`, `hideAllOtherWindows`, or `pruneSession`. A removed key can therefore continue returning its previous label despite no longer existing in `primaryWindows` or `primaryDesiredWindows`.

Advisory observations

- The reversed legacy proxies are constructed without `liveFrameLookup` at [`FloatingPetWindowPool.swift:851`](/Users/cesar/code/codogotchi_p18_06/apps/menubar/Sources/Pool/FloatingPetWindowPool.swift:851). Their `currentFrame` therefore falls back to the `.zero` frame of `NoOpStubWindowController`, so frame-inheritance shadow comparisons can report phantom divergences. This matches the ticket’s stated doc-vs-code drift.

- In new-engine mode, `pruneSession` calls the legacy disk pruner and then calls `SessionPruner.pruneSession` again ([`FloatingPetWindowPool.swift:1930`](/Users/cesar/code/codogotchi_p18_06/apps/menubar/Sources/Pool/FloatingPetWindowPool.swift:1930), [`:1944`](/Users/cesar/code/codogotchi_p18_06/apps/menubar/Sources/Pool/FloatingPetWindowPool.swift:1944)). The operations are mostly idempotent, but slice and sidecar deletion are duplicated.
