### Attack surfaces to probe

1. `PoolDerive.derive`'s per-origin loop (`for (origin, keys) in sessionCapKeysByOrigin`) — the `memory.slotOccupants.subtract(existingOriginSlots)` / `.formUnion(selection.rendered)` resync: does an origin with `sessionCapCandidates` on ONE tick and zero candidates the NEXT tick (e.g. session-pets toggled off, or all its render keys vanish) still get its stale `slotOccupants` entries cleared? The loop only iterates origins present in `sessionCapKeysByOrigin` this tick — an origin absent from that dict this tick never reaches the resync line at all.
2. `evictedFrameDirectives` FIFO drain order in the fresh-key assignment loop (`for key in freshKeys.sorted(by: { $0.rawValue < $1.rawValue })`) — is `WindowKey.rawValue` string-sortable in a way that produces a stable, ticket-intended spawn order across combined/session/origin key shapes, or could two freshly-spawning keys from different origins race for the same origin's queued directive out of documented order?
3. `torndownKeys` release loop (`for key in torndownKeys where key.isSessionKeyed`) — is this reachable/correct when a key is torn down and RE-SPAWNED in the same tick (i.e. present in both `torndownKeys` and `freshKeys`)? Given `torndownKeys = previousKeys.subtracting(visibleFinalKeys)` and `freshKeys = visibleFinalKeys.subtracting(previousKeys)`, these sets are disjoint by construction — confirm there's no code path (e.g. grandfather collapse) where a key could legitimately need release-then-reassign within one tick that this construction silently drops.
4. `hidingAllOthers(keeping:among:)` in `PoolMemoryUserActions.swift` — does it correctly exclude the kept key from the hidden set even when the kept key is `.combined`, and does it hide keys that are session-cap `pendingWindowKeys` (not yet admitted) the same as fully-rendered keys, or does its `among:` parameter's caller-supplied set silently exclude keys the real shell would need hidden?
5. `PromptTimerTracker` observation in the main per-visible-entry loop (`memory.promptTimers[renderKey, default: PromptTimerTracker()].observe(...)`) — this runs BEFORE the TTL-expiry/collapse/cap-selection decisions below it in the same tick. If a key is torn down (TTL-expired or cap-evicted) THIS tick, does its prompt-timer entry linger in `memory.promptTimers` past the eligibility-bound filter (`.combined` is explicitly exempted, but is a torn-down session key's entry pruned only via the `eligibleKeys` filter, and could an evicted-but-still-`lastSeenAt`-eligible key retain a stale timer indefinitely)?
6. `SessionNumberAllocatorState.assign`/`release` and the `setUnlimited` calls scattered in two places (once in the per-origin cap-selection loop, once again in the fresh-key assignment loop) — could calling `setUnlimited` twice per tick for the same origin with a value that changed mid-tick (unlikely but worth probing) leave the allocator's free-list in an inconsistent state relative to already-assigned session numbers from before the cap change?
