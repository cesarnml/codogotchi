### Ticket scope

P18.06 Cutover and role reversal (docs/product/delivery/phase-18/ticket-06-cutover.md)

Outcome:
- The composed pipeline drives the app: `update()` = build tick input → `derive` → `diff` → `apply`, with `PoolMemory` stored on the pool and out-of-band user actions running their pure transitions + immediate effects as the authoritative path.
- Roles reverse: the old pipeline now shadows via the recording proxy's stub direction (stub `currentFrame` reads through to the live windows), with the same comparator and log-only divergence surfacing.
- Launch-time env var `CODOGOTCHI_POOL_ENGINE=legacy` flips the roles back (old drives, new shadows) as the rollback path — read once at startup, no runtime toggling.
- `FloatingPetWindowPool`'s public surface (`setVisible`, `pruneSession`, `hideAllOtherWindows`, `resetPromptTimer`, `sessionNumber`, `sessionDisplayLabel`, `controller(for:)`, `activeOrigins`, `blockedOrigins`, `pendingSessionKeys`, `ttlDismissedWindowKeys`, `replacePet`, `clearAttentionBubbles`, `pruneHiddenKeysWithoutBackingSlice`) is unchanged — `MenubarApp` and menu wiring untouched.
- Full existing suite (900+) green against the composed pipeline — pre-existing behavioral tests are the cutover's primary regression net and must pass unmodified except where they reached into old-pipeline internals.

Rationale (this implementation's actual approach, condensed):
- Extracted the pre-cutover imperative pipeline verbatim into a new `LegacyPoolEngine` class (Stage 1, zero behavior change, verified against the full suite unchanged). A new thin `FloatingPetWindowPool` coordinator class was added in front of it, holding `activeEngine: PoolEngine` resolved once at init from `CODOGOTCHI_POOL_ENGINE`.
- Stage 2 wired the coordinator to drive `PoolDerive` → `PoolDiff` → `PoolApply` with real controller factories when `activeEngine == .new` (default), while `LegacyPoolEngine` is constructed with `NoOpStubWindowController` factories instead — it keeps running every tick unchanged, becoming the shadow. `LegacyPoolEngine`'s own pre-existing `runShadowTick` (built in P18.05) is untouched and keeps producing the same divergence signal, now informative for the reversed direction.
- Several real bugs were found and fixed while composing the pipeline for the first time against the full test suite (not just shadow-comparison): `PoolDiff.diff` didn't detect an own↔minimalist mode flip on the same `WindowKey` (fixed to route through dismiss+spawn); a minimalist window with no injected `minimalistWindowFactory` must fail closed, but `PoolApply.apply`'s spawn closure has no way to express "don't spawn" (worked around by filtering the diff before calling apply); `PoolApply.push` always called `applySessionNumber(nil)` for the combined key (legacy never calls it at all for combined — now key-conditional); the idle-escalation-config push ran after `apply`, double-pushing to windows spawned the same tick (fixed by snapshotting already-open keys before `apply`); `evictedFrameDirectives`/`inheritedFrameFrom` resolves a donor's live `CGRect` lazily from the live controllers dict, which only works for same-tick eviction+respawn — a coordinator-level cross-tick cache (`evictedFrameSnapshots`) was added, gated to only fire when the donor wasn't dismissed in the same tick (to avoid double-adopting on top of `PoolApply`'s own same-tick path); resolved session titles were discarded after `PoolApply.resolveTitles` instead of being fed into `primaryMemory.resolvedSessionTitles`, causing an unbounded re-fetch loop.
- 3 pre-existing tests were marked `XCTSkip` with a tracked-gap comment (not deleted, not silently passed): `PoolDerive` only retains a render key's last-active/TTL-grace immunity while it's still present in the snapshot; a key that vanishes from the snapshot entirely (not just goes idle-past-TTL while still present) loses that immunity, unlike `LegacyPoolEngine` (whose `windows` dict simply isn't touched for an absent key, an implicit behavior derive's pure recompute-from-scratch fold doesn't replicate). Per explicit developer direction, this is deferred to post-P18-landing dogfood QA rather than fixed in this pass.
- 6 other tests were updated (not deleted) to reflect accepted, pre-documented architectural divergences: 4 for the ~1-tick title-resolution delay (Grill-Me decision 3's standing exemption — title resolution is an impure effect pushed to `apply`, one tick behind `derive`'s pure fold), 2 for shared reader/writer closures being invoked once per engine now that both genuinely run every tick (temporary, disappears once P18.07 deletes the old pipeline), plus 4 `MenuItemsTests` fixed at the test-helper level (a test fed a raw `.session(...)` `WindowKey` directly into `perPlatform` without enabling `sessionPetsEnabled`, a combination `resolveRenderKeys` would never actually produce — `PoolDerive` correctly re-derives the fold from customization per its own documented contract, unlike legacy's pool-level fold which trusts whatever key shape it's handed).

### Diff context

The core change is `apps/menubar/Sources/Pool/FloatingPetWindowPool.swift` growing from ~1527 lines (the original single `FloatingPetWindowPool` class) to ~1900 lines split into two classes: `LegacyPoolEngine` (the original class, renamed, logic untouched) and a new `FloatingPetWindowPool` coordinator (~350 new lines). The coordinator's `update()` method, when `activeEngine == .new`:

1. Reads customization/assignments/time fresh (own copies of the reader closures, independent of `legacy`'s).
2. Builds `PoolTickInput` (sessionLabels/knownSessionTitles/sessionPromptSummaries collected from the same injected readers, checking `primaryMemory.resolvedSessionTitles[key] ?? retrievedSessionTitleReader(key)` first).
3. Calls `PoolDerive.derive(input:, memory: primaryMemory)`, reassigns `primaryMemory`.
4. Resolves titles via `PoolApply.resolveTitles`, feeds the result into `primaryMemory.resolvedSessionTitles` directly (fixing a discovered bug).
5. Computes `diff = PoolDiff.diff(desired:, current: primaryDesiredWindows)`.
6. Filters `diff` to fail-closed on minimalist-without-factory.
7. Captures `evictedFrameSnapshots[key] = primaryWindows[key]?.currentFrame` for every `diff.toDismiss` key, before calling apply.
8. Calls `PoolApply.apply(diff:, controllers: &primaryWindows, spawn:)` with real factories.
9. Runs the cross-tick frame-inheritance fallback for donors not dismissed this same tick.
10. Updates `primaryDesiredWindows`, pushes idle-escalation-config changes to previously-open windows only, fires `onMonochromeChanged`/`hiddenKeysSaver` from `desired`.
11. Calls `legacy.update(snapshot: snapshot)` unconditionally — `legacy` was constructed with stub factories, so this drives no real windows but keeps its own `runShadowTick` producing divergence signal.

User-action methods (`setVisible`, `hideAllOtherWindows`, `pruneSession`, `replacePet`, `clearAttentionBubbles`, `resetPromptTimer`, `pruneHiddenKeysWithoutBackingSlice`) each unconditionally call `legacy.<method>` first (the paired shadow effect, exactly as before this ticket), then apply the real-window effect (pure `PoolMemoryUserActions` transition + direct `primaryWindows`/`primaryDesiredWindows` mutation) only when `activeEngine == .new`.

`PoolDiff.diff` gained an `isMinimalist` mismatch check: a key present in both `desired` and `current` with a flipped `isMinimalist` value is now routed to `toDismiss` + `toSpawn` instead of `toUpdate`, since `isMinimalist` is a spawn-time factory choice never re-pushed to an existing controller.

`PoolApply.push` gained a `key != .combined` guard around the `applySessionNumber` call, matching legacy's own combined-window push site which never calls it.
