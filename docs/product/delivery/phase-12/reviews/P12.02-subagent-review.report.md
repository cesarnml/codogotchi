**F1 — Path traversal via unconstrained `session_id`**
File: `packages/contracts/src/slice-entry.ts:19` (`sliceEntrySchema`) and `packages/cli/src/hook-binary.ts:1021–1025` (`sliceFilePath`).

What is wrong: `session_id: z.string().min(1)` imposes no constraint on path characters. `sliceFilePath` concatenates `origin` and `session_id` into a single path component and passes it to `path.join`. Node's `path.join` normalizes `..` within a single string argument, so a session_id of `"../evil"` resolves the final path to a location outside `state.d/`. A crafted stdin payload is sufficient to trigger this: `{"hook_event_name":"PostToolUse","session_id":"../evil"}`.

Finding-discipline clause: clause 2 (correctness gap demonstrable).

Fix recommendation: In `sliceEntrySchema`, tighten the `session_id` validator to exclude path separator characters: `z.string().min(1).regex(/^[^/\\]+$/)`. The schema fix is preferable because it catches the invalid value before any filesystem call.

**Advisory Observations**

**A1 — Concurrent-write test proves in-process I/O interleaving, not multi-process safety.** The test description claims to "prove concurrency safety." In the single-Bun-process scenario, `Promise.all` interleaves microtasks through the same event loop; `withHomeLock` serializes both runHook calls anyway. The multi-process scenario (the actual concurrent risk: two separate platform hook processes writing simultaneously) is not tested. For different-origin concurrent processes, filesystem-level safety via distinct file paths + atomic rename is sufficient and does hold — the test validates the outcome but not the actual multi-process attack vector. Low-priority: the mechanism is correct; the test description overstates what it proves.

**A2 — Swift menubar reader will go dark between P12.02 and P12.03 deploy.** The Swift reader reads `~/.codogotchi/state.json`. P12.02 stops writing it. The pet will freeze on its last rendered state until P12.03 ships the slice-dir reader. The Rationale explicitly defers this ("new reader (P12.03) stops reading it") and notes no real users pre-GA. Surface flagged in case the two tickets ship in separate builds.

**A3 — `deleteSliceBestEffort` naming implies swallow-all but re-throws non-ENOENT.** The "best-effort" naming convention typically implies silent failure. The function re-throws EPERM, EACCES, and all other non-ENOENT codes. Those re-throws are caught and swallowed by `runHookFromStdin`'s outer catch-all, but not by any inner handler. A file permission error on the slice directory would silently absorb without any log or signal. The behavior is defensively correct; the name sets the wrong expectation for the next reader.

**A4 — Only Codex actually sends `hook_event_name: "session_end"` in production; Claude Code session cleanup never fires.** The session_end deletion fires only on the literal string `"session_end"`. Claude Code's terminal events are `"Stop"` (PascalCase) and `"StopFailure"`. Cursor's is `"sessionEnd"` (camelCase). Copilot's is `"agentStop"`. Only Codex uses lowercase `"session_end"`. The P12.02 test uses `{origin: "claude_code", hook_event_name: "session_end"}` — a synthetic payload no real Claude Code session ever produces. In production, Claude Code slice files are never actively cleaned up; they remain in `state.d/` after a session ends with state `"standby"` until P12.03 TTL. This is not a stated invariant gap (Invariant 2 is written in terms of the input condition `hook_event_name === "session_end"`, which is testably true), but the test's cross-origin fixture gives false confidence that "Claude Code sessions get cleaned up." The deferred P12.03 TTL covers this, but the gap is worth naming.

**A5 — Malformed slice files are silently dropped from `globalAggregate` with no diagnostic.** `readSliceDir`'s inner catch swallows all read/parse errors. In a two-origin setup where one origin's slice is corrupted, the aggregate reflects only the remaining origin. The pet could display a stale or incorrect state without any user-visible error. Acceptable per spec (the catch-all is intentional) but difficult to diagnose in production. A future improvement would be to count skipped files and surface the count as a warning in `codogotchi status`.

**A6 — Ticket Outcome and Review Focus claim "schema_version: 7 slice entry" but the on-disk format carries no `schema_version` field.** `SliceEntry` (contracts/src/slice-entry.ts) has no `schema_version` field. The number 7 appears only in `STATE_JSON_SCHEMA_VERSION` and is injected by `globalAggregate → sliceToStateJson` when producing a `StateJsonV1`. The on-disk slice file stores only the fields in `sliceEntrySchema`. The Review Focus asks implementers to "Confirm the writer emits `schema_version: 7`" — it does not; the aggregator does. Tests and implementation are behaviorally correct; only the documentation is imprecise. A one-line clarification in the ticket Rationale or in a contracts comment would prevent future confusion.
