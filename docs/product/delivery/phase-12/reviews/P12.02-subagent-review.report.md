**F1 — Path traversal via session_id in sliceFilePath**
Files: `packages/cli/src/hook-binary.ts` lines 1020–1026 (`sliceFilePath`); `packages/contracts/src/slice-entry.ts` line 19 (`sliceEntrySchema`).
What is wrong: `session_id` is validated as `z.string().min(1)` — no restriction on `/` or `..`. When a hook payload supplies `session_id: "foo/../../evil"`, Zod accepts it, `path.join(sliceDirPath(home), "claude_code:foo/../../evil.json")` resolves to `home/evil.json`, and `writeFile` writes there instead of inside `state.d/`. Greater depth (`"foo/../../../evil"`) escapes `home` entirely. The same crafted value passed to `deleteSliceBestEffort` attempts an `unlink` on the traversed path, though an ENOENT there is swallowed.
Clause: Finding-discipline clause 2 (demonstrable correctness gap — file lands at the wrong path) and clause 3 (the `z.string().min(1)` spec literally permits the unsafe value; the ticket Rationale does not acknowledge this).
Recommended fix: Add a path-character constraint at the schema boundary in `sliceEntrySchema`: change `session_id: z.string().min(1)` to `session_id: z.string().min(1).regex(/^[^/\\]+$/, "session_id must not contain path separators")`. This is the only write-gating point; fixing it here also covers `deleteSliceBestEffort`, which reuses the same `sliceFilePath` helper. Do not rely solely on caller-side sanitization.

**Advisory Observations**

Both `writeSliceAtomic` and `writeCounters` execute inside `withHomeLock`. For cross-origin writes, the per-origin distinct filename makes the lock unnecessary for the slice write itself (atomic rename is sufficient). The lock is required only to protect the shared `.hook-counters.json`. Consequence: two hooks from different origins that arrive simultaneously must still serialize through one process-wide directory lock, adding latency proportional to the number of concurrently active agents. No correctness issue; flag for reviewers evaluating performance under simultaneous multi-agent use.

The concurrent-write test title ("proves concurrency safety") overstates what a single-process `Promise.all` demonstrates. The test proves same-process async I/O interleaving leaves both slice files intact; it does not prove multi-process OS-level safety. That safety comes from the atomic-rename-on-distinct-filenames property, which is an OS invariant that no JS test can directly exercise. The comment in the test should narrow its claim to "proves same-process I/O interleaving" to avoid misleading future readers about what the test actually asserts.

`readSliceDir`'s inner catch silently drops any unreadable or JSON-malformed slice file. Dropped slices produce no log line and no observable failure — the aggregate just returns a potentially older entry. If a future migration introduces a new slice shape that fails `JSON.parse` (or if a buggy writer produces truncated JSON), the failure would be invisible at runtime. Consider adding a debug-level log on the catch path gated behind a `CODOGOTCHI_DEBUG` env var; this costs nothing in the normal path and provides a diagnostic ladder when stale-display bugs are reported.

The `readSliceDir` path in `status.ts` does `JSON.parse(raw) as SliceEntry` (a type cast) rather than `sliceEntrySchema.parse`. A valid-JSON-but-schema-invalid file (e.g., written by a future schema-7.1 writer with extra required fields) is silently accepted and passed to `globalAggregate`. If `updated_at` is present but `activity_state` is not a valid enum value, `globalAggregate` might pick that entry as the winner and produce a `StateJsonV1` with an unknown activity state. Adding a `sliceEntrySchema.safeParse` guard on read (dropping the invalid slice rather than using it) would make `readSliceDir` consistent with `writeSliceAtomic`'s validation discipline. This is a forward-compatibility concern, not a current-state defect.
