**Actionable findings**

**F1 — `globalAggregate([])` returns a mutable alias of `IDLE_DEFAULT`**
File: `packages/contracts/src/slice-entry.ts`, line 81.
Clause: Finding discipline 2 — demonstrable correctness gap. A caller mutating the returned object corrupts the module-level constant, causing all subsequent empty-set calls to return the corrupted value. Fix: return a shallow copy — `return winner ? sliceToStateJson(winner) : { ...IDLE_DEFAULT }` — or `Object.freeze(IDLE_DEFAULT)` at declaration and return the frozen const (callers would receive a TypeError on mutation attempt, which is acceptable for a sentinel). Given `StateJsonV1` has no nested mutable references that change semantics, a shallow spread is sufficient.

**F2 — `latestSlice` tiebreak is not offset-safe**
File: `packages/contracts/src/slice-entry.ts`, lines 69–73.
Clause: Finding discipline 3 — spec permits real bug. The `sliceEntrySchema` explicitly accepts `z.string().datetime({ offset: true })`, so a non-UTC `updated_at` is contract-valid. The string comparison `candidate.updated_at > winner.updated_at` is chronologically correct only when all timestamps share the same UTC offset. A writer using local time (e.g., `+07:00`) against an existing `Z`-suffix slice can produce an incorrect winner: `"2026-06-28T23:00:00+07:00"` (16:00 UTC) beats `"2026-06-28T17:00:00Z"` (17:00 UTC) by string comparison, choosing the older moment. All current writers use `new Date().toISOString()`, so this does not fire in production today, but any future writer that uses `Date` formatted with a local offset (e.g., `toLocaleString` with ISO format, or a Rust/Swift system-clock writer emitting local time) will silently pick the wrong winner without any error. Fix: normalize before comparison — `new Date(candidate.updated_at).getTime() > new Date(winner.updated_at).getTime()` — or document a hard requirement that `updated_at` must be UTC-`Z`-suffix only, enforced by a schema refinement (`.refine(s => s.endsWith('Z'))`).

**Advisory Observations**

- **Equal-`updated_at` tie behavior is untested and undocumented.** When two slices share an identical `updated_at` string, `latestSlice` returns the first-in-array winner (strict `>` means the second never displaces the first). This is a deterministic and defensible choice, but the tests do not cover it and the Rationale does not mention it. If a multi-session writer batches a flush at the same millisecond, the tie-resolution is array-order-dependent. Not a current production risk, but worth a test assertion and a comment on `latestSlice` to lock the contract.

- **Optional field round-trip coverage is absent in the test suite.** `slice-entry.test.ts` tests that optional v5 RPG fields are accepted by `sliceEntrySchema`, but no test passes a slice with populated optional fields through `globalAggregate` and asserts those fields appear on the returned `StateJsonV1`. A silent regression in `sliceToStateJson` (e.g., accidentally removing `active_minutes`) would not be caught by any existing test. Adding one round-trip test that populates all optional fields and reads them back off the reducer output would close this gap.

- **Inline attention schema duplication creates a maintenance coupling.** The `attentionSchema` in `slice-entry.ts` and the inline `attention` object schema in `stateJsonV1Schema` are currently identical, but they are structurally independent Zod schemas. A future PR adding a new `reason_kind` to `stateJsonV1Schema` that omits updating the inline copy in `slice-entry.ts` would cause slice validation to accept fewer reason kinds than the canonical schema — silently, with no TypeScript error. An extraction of a shared `attentionSchema` into a dedicated file (or into `state-json.ts` as an export) would eliminate the risk. The Rationale explicitly chose inline to avoid re-exporting from `state-json.ts`; that is a valid tradeoff, but a cross-schema equality test (asserting both inline schemas accept and reject the same payloads) would make the coupling explicit and catch future drift at test time.
