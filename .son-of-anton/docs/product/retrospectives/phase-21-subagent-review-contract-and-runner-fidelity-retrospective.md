# Phase 21 — Subagent-Review Contract and Runner Fidelity — Retrospective

## 1. Scope delivered

Seven tickets, stacked PRs [#111](https://github.com/cesarnml/son-of-anton/pull/111) (P21.01), [#112](https://github.com/cesarnml/son-of-anton/pull/112) (P21.02), [#113](https://github.com/cesarnml/son-of-anton/pull/113) (P21.03), [#114](https://github.com/cesarnml/son-of-anton/pull/114) (P21.04), [#115](https://github.com/cesarnml/son-of-anton/pull/115) (P21.05), [#116](https://github.com/cesarnml/son-of-anton/pull/116) (P21.06), and this ticket's PR (P21.07), on branch stack `agents/p21-01-*` through `agents/p21-07-*`. Delivered: a strict tag-based parser for `subagent-review.report.md` replacing heading-detection (P21.01); an `completed_with_findings` outcome so a findings-bearing report can never silently record `clean` (P21.02); a broadened fallback trigger so a runner that spawns but produces no usable review advances the chain instead of stalling, with a write-violation guard added mid-ticket via adversarial review (P21.03); per-platform `subagentRunnerOptions` config and flat `--subagent-model`/`--subagent-effort` flags with ledger fidelity (P21.04); a `subagent_review_recorded` notification event mirroring `review_recorded`, including the previously-unwired doc-only auto-skip path (P21.05); multi-issue `Origin issue:` parsing and multi-`Closes` PR bodies (P21.06); and this ticket — a full accounting of codogotchi's 55-row review-gap ledger, two new promoted diff-derived classes in `adversarial-review-template.md` (8 and 9), and phase closeout docs.

## 2. What went well

**The refactor-review → adversarial-review two-gate sequence caught real bugs, not just style nits, on nearly every ticket.** P21.03's adversarial pass found that broadening the fallback trigger to include `ran + runner_failed` also let a write-violating first attempt (which should stop the chain per the advisory-only contract) get masked by a later successful fallback — a genuine correctness regression introduced by the ticket's own change, not a pre-existing issue. P21.05's pass found the doc-only auto-skip path never emitted its notification, an omission a spec-conformance read would have missed since the spec didn't call out that specific branch. P21.06's pass found a fence-unaware `## Epic` section boundary — a bug that could only exist because P21.06 introduced section-scoping for the first time (the prior parser never scoped at all). In each case the finding was demonstrable, testable, and fixed within the same review cycle. The adversarial prompt's "attack surfaces" section, hand-authored per ticket from the actual diff rather than generic, is what made these findings specific enough to act on immediately rather than requiring a follow-up round.

**Verifying red state by literally stashing implementation and re-running tests, rather than trusting "I wrote the test first,"** caught nothing wrong in this phase but is worth naming as the reason every `post-red` gate passed cleanly on the first attempt — the discipline of `git stash push -- <impl files>`, run tests, confirm failure, `git stash pop` is cheap and removes all ambiguity about whether a red commit is honest.

**Count verification against source data, not against a pre-existing summary, changed a real decision in P21.07.** Codogotchi's `promotion-queue.md` claimed `control-signal-starved-by-change-gated-callback` was "AT THRESHOLD (3×)"; reading the cited third ledger row directly showed it was classified `completeness-gap`, not `review-reachable`. The class was still promoted (2 confirmed occurrences meets the stated "≥2–3×" bar), but the clause and the analysis doc record the corrected count rather than repeating the overclaim. This is the same discipline the ticket's own Review Focus asked for ("verify... directly against ledger rows... rather than trusting the queue") and it caught something real on the first application.

## 3. Pain points

**Avoidable waste: the refactor-review reconciliation gate produced a false-positive "Condition A" block on every single ticket in this phase (P21.03 through P21.06), always for the same reason.** The orchestrator's own `chore(...): record refactor-review runner artifact` bookkeeping commit — written automatically when `subagent-refactor-review` records an outcome — touches `reviews/*.ledger.json`, which is itself inside the ticket's `reviewedPaths` (since the prompt file was part of the same diff). `reconcile-subagent-refactor-review` then sees an unlabeled commit touching reviewed paths since the last recorded row and blocks, even though that commit is the orchestrator's own artifact-recording action, not undisclosed refactor work. The workaround (`record-deferred` with an explanatory reason) is a two-command detour on every single ticket, not a rare edge case. This is a tooling gap worth fixing upstream: `detectRefactorReviewLabeledCommits`'s `reviewedPaths` set (or the reconciliation check itself) should exclude the orchestrator's own `reviews/**` bookkeeping commits, since they can never carry undisclosed code changes by construction.

**Expected cost: writing a genuinely adversarial, diff-specific prompt for every ticket (both the refactor-review and adversarial-review gates) is real, non-compressible work** — roughly as much authoring effort as the ticket's own implementation, on a 2-3 point ticket. This is by design (a vague "find holes" prompt produces vague findings) but it means ticket cycle time scales with prompt-authoring care, not just code-change size. Worth budgeting for explicitly rather than treating review-gate authoring as overhead.

## 4. Surprises

**A mid-phase cherry-pick request landed cleanly with zero conflicts.** The operator asked to cherry-pick an unrelated main-branch commit (`a5e81438`, a codogotchi-gate emission fix) into the in-progress P21.06 worktree partway through that ticket's implementation. Because the cherry-picked commit touched only `cli-runner.ts`/`codogotchi-gate.ts`/its own test file, and the in-flight uncommitted P21.06 changes were confined to `planning.ts`/`state.ts`/`types.ts`/`pr-metadata.ts`, there was no file overlap and `git cherry-pick` applied without touching the working tree's uncommitted state. Not something to rely on in general, but confirms that surgical single-file-scoped hotfixes can be threaded through an in-progress ticket worktree safely when their file footprint is checked first.

**The review-gap ledger's own promotion-queue document was stale relative to its ledger — by design, not by neglect.** Three rows (`codogotchi-43`, `-44`, `-45`, dated 2026-07-14) described a clear, 3×-recurring, all-`review-reachable` defect family (source identity collapsed into a folded render target) that had never been added to `promotion-queue.md` at all — the queue simply hadn't been updated since those rows landed. This is exactly the gap the review-gap-ledger system is supposed to have someone periodically close, and P21.07 is that periodic close for this cycle. Future phases doing this kind of ledger-mining work should expect to find un-queued recurring classes, not just verify already-queued ones.

## 5. What we'd do differently

**The `## Epic` section extraction in P21.06 was written and shipped once (whole-document match, then narrowed to Epic-only after refactor-review, then made fence-aware only after adversarial review) across three separate passes on the same function, each catching a real gap the previous pass missed.** With the fence-awareness requirement anticipated from the start (markdown sections containing fenced code blocks are common enough in ticket/plan docs to expect), the function could have been written fence-aware in the Green step, saving two follow-on review-driven rewrites. The lesson generalizes: when parsing a "section" out of markdown for a strict/security-relevant purpose (as opposed to display), assume the section can contain fenced code and design the boundary-detection with that from the first pass, rather than treating it as an edge case to patch in after review.

## 6. Net assessment

The phase's stated product contract — honest outcome recording, a fallback chain that actually advances on runner failures, per-platform model/effort control, developer notification on every recorded outcome, multi-issue closing, and a review-gap-ledger-informed prompt update — shipped in full across all seven tickets, with every ticket passing its own adversarial review clean (after prudent patches) and full CI green throughout. The two-gate review discipline (refactor-review for local quality, adversarial-review for correctness) demonstrably earned its cost this phase: every ticket except doc-only P21.07 had at least one genuine, ticket-introduced bug caught and fixed before merge, none of which would have been caught by tests alone since each was a gap in what the tests asserted, not a failure of an existing assertion.

## 7. Follow-up

Route through a standalone PR or a small future ticket in the delivery-orchestrator's own backlog.
- `compound-widget-cohesion-under-transform` and the `pool-refactor-dropped-single-owner-behavior` family remain flagged as phase-integration-pass candidates (not adversarial-review clauses) in `docs/product/review-gap-analysis/codogotchi-ledger-2026-07.md` — a future ticket should define the lightweight phase-closeout integration checklist these belong on; not designed in this phase.
- Re-run this same ledger-mining exercise on a future cadence (e.g. every 3-4 phases, or when the ledger crosses another ~10-row threshold) rather than waiting for another dedicated ticket to notice the promotion queue has drifted from the ledger.
