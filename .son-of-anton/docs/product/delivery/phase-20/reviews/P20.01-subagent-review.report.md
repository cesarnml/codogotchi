# Actionable findings

1. `tools/delivery/types.ts` — `TicketState` has no field tracking the refactor review’s reviewed-head SHA. The ticket explicitly requires new ticket-state fields for “prompt path, outcome, and reviewed-head SHA,” while the implementation adds the first two categories but not the third. This breaks the stated ticket outcome under finding-discipline clause 1. Add a distinct optional field such as `refactorReviewHeadSha?: string` or `refactorReviewReviewedHeadSha?: string`, using the name expected by P20.02’s state-writing path, plus a type-level/state round-trip test.

2. `tools/delivery/refactor-review.ts` — `parseRefactorSuggestions` treats `normalized === ''` as explicit `None`, and `isSuspiciousRefactorSuggestionsParse` ignores `closed`. Consequently, an empty tag block or an unclosed `<refactor-suggestions>None` block suppresses the required zero-parse/malformed-contract warning. This breaks invariant 3 and the referenced parser contract’s requirement that malformed/unclosed output warn. Set `isExplicitNone` only when a properly closed body is literally `None` according to the chosen punctuation/case contract, and make `!result.closed` suspicious regardless of parsed contents. Add empty-body and unclosed-`None` regressions.

3. `tools/delivery/refactor-review.ts` — Raw first-occurrence tag matching can parse a code-fenced or prose example as the authoritative result. For example, an example skeleton containing placeholder bullets before the real report block yields false suggestions; an example containing `None` can hide a later malformed or missing result. This is a demonstrable ticket-parser correctness gap under clause 2. Restrict recognition to the actual output region or implement fence-aware selection of one authoritative balanced tag block, rejecting or warning on ambiguous multiple blocks. Add code-fence, inline/prose, and multiple-block tests.

4. `tools/delivery/refactor-review.ts` — `reconcileRefactorReview` returns `patched` as soon as any `[refactor-review]` commit touches any reviewed path. If that commit touches `a.ts` while a later unlabeled commit touches reviewed `b.ts`—or later changes the same file—the unlabeled reviewed change bypasses Condition A. This defeats the ticket’s silent-lie protection and is a correctness gap under clause 2. Compute changed reviewed paths first and require the qualifying labeled commits to account for all relevant post-review reviewed-path changes, including changes occurring after the last qualifying commit; otherwise return Condition A. Add mixed-path and labeled-then-unlabeled tests.

5. `tools/delivery/refactor-review.ts` — `validateRefactorSuggestionDecision` does not validate `decision` at runtime and accepts IDs such as `"foo"`. A JSON/CLI-derived row cast into the exported type can therefore pass with `decision: "ignored"` and no reason, contrary to the required `R1`, `R2`, … and accepted/rejected/deferred ledger shape. This is a demonstrated boundary-validation correctness gap under clause 2. Validate `id` against the intended `^R[1-9]\d*$` form and validate `decision` against the three allowed values before applying reason rules; add runtime-invalid tests.
