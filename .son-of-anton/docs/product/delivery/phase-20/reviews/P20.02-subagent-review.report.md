# Surface results

1. [probed] `runnerWroteFiles` snapshots only dirty path names. If `foo.ts` is dirty before the run and the runner changes `foo.ts` again, the before/after sets are identical and the review is recorded clean. A timed-out runner’s writes can likewise become the fallback runner’s baseline and evade detection.

2. [probed] `resolveRefactorReviewPromptContent` always emits fixed headings and instructions exceeding the validator’s 80-character floor. With an unreadable ticket and failed diff lookup, `(ticket spec unavailable)` and `(no changed files detected)` still pass validation, despite not being a primary-authored filled template.

3. [probed] First-ever `record-deferred` resolves `reviewedHeadSha` to `unknown` without throwing. Reconciliation then runs git commands against `unknown`; their non-zero statuses are ignored, empty stdout becomes empty path/commit sets, and reconciliation can report the ledger consistent.

4. [probed] `resolveInternalReviewPatchCommits` uses the supplied suffix dynamically in `subject.endsWith(\` ${suffix}\`)`; `[refactor-review]` is accepted without an old-literal runtime check.

5. [probed] Implicit reconciliation selects the first `verified` ticket, then the first `in_review` ticket. The documented one-ticket-per-worktree workflow lowers the likelihood, but it does not make selection unique when state contains multiple matching tickets; passing the ticket ID avoids ambiguity.

6. [probed] Refactor dispatch uses the same `git rev-parse HEAD` shape as adversarial dispatch. Both ignore non-zero `spawnSync` status and accept empty stdout, so a missing/broken worktree disables deduplication and can later record an empty reviewed SHA rather than failing.

7. [probed] `readSubagentRunnerArtifact` and `validateRunnerArtifact` validate JSON content, not filename suffix or directory. Refactor ledgers using the shared schema parse normally.

8. [probed] `--prompt-file`, `--force`, `--subagent`, `--primary`, and `--reason` are all parsed into the shared object/set and consumed. The command usage text in `cli.ts` does not list the new commands, but flag parsing itself is wired.

9. [probed] The broad catches introduce a refactor-specific silent-success path: reconciliation swallows corrupt artifacts, invalid SHAs, missing worktrees, and failed git plumbing, then prints “ledger is consistent.” The prompt auto-builder similarly converts actionable read failures into validator-passing fallback prose.

10. [probed] Real `spawnSync` may return `status: null`, populated `error`, or empty stdout without throwing. The runner handles `ENOENT`, but HEAD/status/diff closures do not validate status or error, allowing malformed empty values to be treated as legitimate repository state.

11. [probed] Report and trace writes have the same newline and trace-content behavior as the adversarial helper. They also share its write-before-ledger/commit atomicity window. The trace file is not included in `alsoCommitAbsolutePaths` in either path, so the refactor path does not introduce a distinct regression.

12. [probed] Tests assert exact prompt argument identity, outcome enums, state fields, and basic ledger rows. They distinguish helper-level runner and recorder behavior, but do not exercise CLI dispatch without `--subagent`, first-ever deferred reconciliation, same-path rewrites, timeout/fallback writes, command-side ledger persistence, or the reconciliation command’s Condition A/B behavior.

13. [probed] The ticket Rationale remains the placeholder despite the implementation documenting a deliberate status-machine trade-off in `tools/delivery/refactor-review.ts`. Repo policy says behavior or trade-off changes belong in `## Rationale`, so this decision should be recorded there.

# Actionable findings

- `tools/delivery/subagent-runner.ts:1273` — Advisory-write detection compares only dirty path membership and skips detection entirely for timed-out attempts. A runner can modify an already-dirty file, or write before timing out and falling back, yet the final result can be `clean`. This breaks invariant 4 and finding-discipline clause 1. Snapshot content-sensitive git state before every attempt—such as porcelain plus staged/unstaged diff hashes and untracked content metadata—and compare it after every attempt, including timeout/unavailable paths, before allowing fallback or a clean outcome.

- `tools/delivery/cli-runner.ts:1359` — Runner-versus-recorder dispatch ignores whether `parsed.subagent` was supplied. With `subagentRunner` configured, `subagent-refactor-review P20.02` launches a runner despite no `--subagent`; without configuration it throws a runner-selection error instead of requiring `clean|patched <sha>`. This breaks invariant 2. Gate runner mode explicitly on `parsed.subagent`; otherwise require and record the explicit outcome/SHA pair.

- `tools/delivery/cli-runner.ts:3187` — The no-`--prompt-file` fallback passes validation even when neither ticket content nor diff information was successfully read, and it is generated boilerplate rather than a primary-authored filled `refactor-review-template.md`. This breaks invariant 1 and the ticket outcome. Require `--prompt-file`, or load a genuinely filled primary-authored artifact; at minimum fail when the ticket read or git diff command fails and strengthen validation around required customized sections.

- `tools/delivery/cli-runner.ts:1311` and `tools/delivery/cli-runner.ts:3249` — First-ever `record-deferred` writes `reviewedHeadSha: "unknown"`. Git failures caused by that sentinel are converted to empty result sets, after which `reconcile-subagent-refactor-review` prints success. This is a demonstrated silent-failure correctness gap under finding-discipline clause 2. Resolve a real ticket-worktree HEAD for the first deferred row, validate it as a commit, and make reconciliation reject sentinels, corrupt artifacts, non-zero git statuses, and empty HEAD results.

- `tools/delivery/cli-runner.ts:1384` and `tools/delivery/cli-runner.ts:1497` — HEAD resolution treats non-zero `spawnSync` results as successful empty strings because `spawnSync` generally does not throw for git exit failures. This disables no-op deduplication and can persist an empty reviewed SHA. Under finding-discipline clause 2, validate `status === 0`, absence of `error`, and non-empty stdout; otherwise throw an actionable worktree/git error.

# Advisory Observations

- `docs/product/delivery/phase-20/ticket-02-refactor-review-cli-commands.md` leaves `## Rationale` unfilled, while `tools/delivery/refactor-review.ts` records the deliberate decision not to transition ticket status. That is an implementation trade-off and should be appended to the ticket Rationale under the repo’s completion policy.

- `tools/delivery/test/p20-02.test.ts` tests the underlying helpers rather than the new CLI cases. Its “recorder mode (no --subagent)” test directly calls `recordRefactorReviewOutcome`, so it cannot detect the actual CLI dispatch bug.

- The new commands are absent from `getUsage()` in `tools/delivery/cli.ts`. The ticket explicitly defers the orchestrator command-reference table to P20.03, but it does not explicitly defer CLI help output.

- Implicit reconciliation remains order-dependent when multiple tickets share `verified` or `in_review`. Explicit ticket IDs are currently the reliable way to avoid selecting the wrong ticket.
