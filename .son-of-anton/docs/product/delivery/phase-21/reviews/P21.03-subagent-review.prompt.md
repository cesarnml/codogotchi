### Ticket scope

P21.03 Fallback advances on ran-but-failed runners

`runSubagentWithFallback` (`tools/delivery/subagent-runner.ts`) advances to the next
runner in `buildSubagentFallbackOrder` when an attempt returns `status: 'ran'` with
`terminatedReason` in `{runner_failed, rate_limit, sandbox_denied}` — the issue #105 case
where the CLI spawns and exits but the backing model produced no usable review.
`advisory_violation` does **not** advance the chain: the runner reviewed but broke the
no-writes contract; the violation records honestly (as today) and stops.
`skipped` with `fallbackLevel: 'failed_all'` is recorded only when every runner in the
chain fails to produce a usable review; every attempt remains auditable in
`attemptedKinds` and the ledger.
A successful fallback records `fallbackFrom` = the originally requested runner and
`fallbackLevel: 'fallback'`, exactly as the existing unavailable/timeout path does.
`docs/template/delivery/delivery-orchestrator.md`'s fallback description reflects the
broadened trigger set.

Rationale (from the ticket doc): the change broadens `shouldFallbackToOtherRunner` to
also return `true` for `ran` results with the three failure `terminatedReason`s, and
gates the loop's early-return in `runSubagentWithFallback` on that same predicate — the
smallest change; loop shape and `attemptedKinds`/`fallbackLevel` bookkeeping were
untouched. `advisory_violation` is decided *after* the fallback loop returns, by
`decideAdvisoryRunnerOutcome`, from write-detection state (`runnerWroteFiles`) rather than
from `terminatedReason` on the attempt result — so it structurally never reaches the new
in-loop check, and the loop's existing "ran + not-in-the-fallback-set" branch already
stops on it (a `ran` attempt whose write-violation is caught later still reports
`terminatedReason: 'completed'` at the loop-attempt level, per `tryRunner`'s classifier).

A pre-existing test describe block (`P11.04/P21.03 — auto-fallback predicate covers
binary-availability failures and ran-but-failed runners` in
`tools/delivery/test/p11-04.test.ts`) previously asserted the exact old, narrower
contract this ticket reverses (`ran` + `rate_limit`/`sandbox_denied` must NOT fall back);
its two `it` blocks were flipped to assert the new `true` outcome, and the file-header
comment and describe title were updated to match.

Refactor-review pass (cursor-cli, advisory, clean) suggested and the primary agent
accepted two doc/naming fixes: extending `runSubagentWithFallback`'s JSDoc to name the
P21.03 triggers, and renaming the P11.04 describe title/file-header invariant #3 to
match the broadened contract. A third suggestion (merging the `ran()`/`ranWith()` test
helpers in `subagent-runner.test.ts` into one parameterized helper) was deferred as
low-value test-only duplication, not correctness-relevant.

### Invariants to hold

1. `shouldFallbackToOtherRunner` returns `true` for a `ran` result if and only if
   `terminatedReason` is `runner_failed`, `rate_limit`, or `sandbox_denied` — it must
   return `false` for `ran` + `completed` and for `ran` + `advisory_violation` (the
   ticket's explicit "does not advance" case), and `true` for `unavailable`/`timeout`
   exactly as before.
2. `runSubagentWithFallback` never invokes a given runner kind more than once per call —
   `attemptedKinds` has no duplicates regardless of how many attempts return a
   fallback-triggering result.
3. A `ran` + `completed_with_findings`-eligible result (i.e. a `ran` attempt whose
   `terminatedReason` is `completed`) must return immediately with no fallback — the
   `completed_with_findings` vs `clean` distinction is decided later by
   `decideAdvisoryRunnerOutcome`/`hasHonestFindings`, and this loop-level change must
   not alter that downstream classification for any `terminatedReason: 'completed'`
   attempt.
