### Ticket scope

P21.04 Per-platform model and effort selection with ledger fidelity

`orchestrator.config.json` accepts an optional `subagentRunnerOptions` per-platform map:
`{ "claude-cli": { "model": string?, "effort": string? }, "codex-cli": { "model": string?,
"effort": string? }, "cursor-cli": { "model": string? } }`; unknown platforms or option
keys fail config validation with actionable errors.

`subagent-review` accepts flat `--subagent-model <value>` and `--subagent-effort <value>`
flags that apply **only to the explicitly requested runner** (via `--subagent` or
configured `subagentRunner`); fallback runners resolve from `subagentRunnerOptions`
alone. Precedence per platform: flag (requested runner only) > config entry > platform
default.

`buildRunnerSpawnCommand` forwards resolved values into each platform's documented
flags: `claude --model <m> --effort <e>`, `codex exec -m <m> -c
model_reasoning_effort=<e>`, `agent --model <m>` (cursor-cli has no effort flag — effort
rides the model slug).

Values a platform cannot express fail fast before spawn (e.g. `--subagent-effort` with
`cursor-cli` requested, or an effort entry under `subagentRunnerOptions["cursor-cli"]`)
— no silent dropping.

`SubagentRunnerInvocation` ledger rows gain optional `runnerModel` and `runnerEffort`
recording what actually ran (`null`/absent when platform default); recorded for
fallback attempts too, from that platform's config entry.

Rationale (from the ticket doc): one resolver (`resolveRunnerOptions`) returning
`{model?, effort?}` per attempt, consumed uniformly by the P21.03 fallback loop via the
same `attempt(runner)` closure already present at the `subagent-review` call site.
Resolution was deliberately kept out of `runSubagentWithFallback`/
`shouldFallbackToOtherRunner` themselves — those functions have no access to the
*requested* runner identity needed to know when a flag applies, nor to repo config.
Intentionally deferred: the `subagent-refactor-review` gate
(`runProgrammaticSubagentReview`) still calls `buildRunnerSpawnCommand` without
model/effort options — the ticket text scopes the flat flags to `subagent-review`
specifically.

A refactor-review pass (cursor-cli, advisory) found and the primary agent accepted all
six suggestions: `ResolvedRunnerOptions` in `subagent-runner.ts` now aliases
`SubagentRunnerOptionEntry` from `config.ts` (was a structurally-identical duplicate
type); `resolveRunnerOptions`'s cursor-cli-only effort rejection now checks
`RUNNERS_SUPPORTING_EFFORT` (imported from `config.ts`) instead of a hardcoded
`=== 'cursor-cli'` string comparison; `parseSubagentRunnerOptions` in `config.ts` now
calls the existing `optionalNonBlankString` helper instead of inline `typeof`/`trim()`
checks; the `cli-runner.ts` closure variable `resolvedRunnerOptionsForAttempt` is now
typed as the imported `ResolvedRunnerOptions` instead of an inline duplicate shape; a
pre-existing (not introduced by this ticket) stale `usedRunner: 'claude-cli' |
'codex-cli' | 'skipped'` type annotation — which could never actually hold `'cursor-cli'`
even though `fallbackOutcome.ranKind` can be that value — was widened by dropping the
explicit annotation and letting it infer; a test was added asserting the explicit-`null`
`runnerModel`/`runnerEffort` round-trip matching the production `?? null` call-site
shape, and the prior "absent" test was renamed for accuracy.

### Invariants to hold

1. `resolveRunnerOptions` applies `flagModel`/`flagEffort` if and only if
   `runner === requestedRunner`; a fallback attempt (`runner !== requestedRunner`)
   resolves purely from `configOptions` for its own platform and never sees the
   originally-requested runner's flag values, regardless of call order or which runner
   is requested.
2. A resolved `effort` value for a platform not in `RUNNERS_SUPPORTING_EFFORT`
   (currently only `cursor-cli`) must throw before any process spawns — whether the
   `effort` came from a CLI flag on the requested runner or from a `subagentRunnerOptions`
   config entry consulted for a fallback attempt.
3. `SubagentRunnerInvocation.runnerModel`/`runnerEffort` on the ledger row written by
   the `subagent-review` command reflect the model/effort actually used by whichever
   runner ultimately produced the recorded outcome (the winning attempt on success, or
   the last attempted runner on `failed_all`) — not the originally-requested runner's
   resolved values when a fallback fired.

### Attack surfaces to probe

1. `resolveRunnerOptions` (tools/delivery/subagent-runner.ts): the `isRequested`
   ternaries compute `model`/`effort` independently — could a partial override (flag
   sets `model` but not `effort`, or vice versa) on the requested runner accidentally
   fall through to reading the *config* entry for the other field when it shouldn't, or
   leak a `false`-y-but-defined value incorrectly given `??` short-circuits only on
   `undefined`, not `''`?
2. `tools/delivery/cli-runner.ts`'s `subagent-review` attempt closure (~line 1044+):
   `resolvedRunnerOptionsForAttempt` is reassigned on every loop iteration by
   closure mutation. If `resolveRunnerOptions` throws (cursor-cli + effort) partway
   through a multi-runner fallback chain, does the thrown error propagate cleanly out of
   `runSubagentWithFallback`'s `attempt()` callback and abort the CLI command, or could
   it be silently swallowed by `tryRunner`'s `catch` (which currently only wraps the
   `spawnProcess()` call, not the `resolveRunnerOptions` call sitting just before it)?
3. `buildRunnerInvocation`'s ledger write (~line 1285 area): `runnerModel:
   resolvedRunnerOptionsForAttempt.model ?? null` — when the fallback chain ends in
   `failed_all` (every runner failed), does this still correctly record the *last
   attempted* runner's resolved options, or could `resolvedRunnerOptionsForAttempt`
   retain a stale value from an earlier, non-final attempt if the loop's iteration order
   or early-exit behavior changed under P21.03's broadened fallback triggers?
4. `parseSubagentRunnerOptions` (tools/delivery/config.ts): validation order is
   platform-key check → entry-shape check → entry-key check → model check → effort
   check (which itself checks platform-support before value-shape). Can a config with
   `subagentRunnerOptions: { "cursor-cli": { "effort": "" } }` (blank string, not
   present but empty) produce a confusing double-error path or an unclear message,
   since the platform-support check fires before the blank-string check?
5. `RUNNERS_SUPPORTING_EFFORT`/`VALID_CLAUDE_EFFORT_TIERS` cross-module import
   (`subagent-runner.ts` now imports from `config.ts`): does this introduce or risk a
   circular import given `cli-runner.ts` imports both modules, and does
   `resolveOrchestratorConfig`'s default-merging (used by tests that construct a
   `ResolvedOrchestratorConfig` by hand, e.g. `baseConfig` in
   `runtime-config.test.ts`) still work when `subagentRunnerOptions` is entirely
   absent from a config object?
